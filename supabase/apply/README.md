# Historical SQL bundles — disabled, do not apply

The checked-in `fresh-install.sql` and `upgrade-hardening.sql` are stale and are **not** verified as safe for a new installation or an upgrade. Each now deliberately raises an exception inside its transaction before executing any bundled migration. The generator `npm run build:apply-sql` is also disabled and does not write files. These protections are on this draft branch; main and older revisions retain their previous behavior. Removing the guard, selectively executing a portion of a file, or using an older copy bypasses it and is unsafe.

The hosted project has different migration versions and combined migrations; never blindly apply these bundles or run `supabase db push`. Historical `preflight.sql`, `verify-live.sql`, and `seed-cleanup.sql` are not a comprehensive reconciliation or recovery plan. In particular, `seed-cleanup.sql` contains destructive operations and must not be run without a reviewed, specifically authorized plan. The current read-only PR #103 checks are under `supabase/preflight/` and their limitations are documented in `docs/PR103_SCHEMA_REHEARSAL.md`.

See `docs/CLIENT_CHANGE_PLAN.md` for the actual current status. A future replacement must be designed and tested for its intended target and account/permission dependencies; parsing SQL or comparing only listed source hashes does not establish a complete or safe bundle. The excluded demo seed contains public demo credentials and must not be applied to a client project.
