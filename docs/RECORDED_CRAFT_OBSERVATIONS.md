# Craft observed at record entry — development candidate

**Installed on the development database** as `20261114021011_development_recorded_craft_observations`, after a rollback-only pinned-artifact rehearsal and empty assured-Founder reads. The category cutover keeps a current worker craft and immutable category-change events, but the earlier attendance and batch-payslip queries returned the current craft even for old records. This candidate records the worker's current position when a new attendance row or payroll voucher is first inserted. It does not rewrite attendance, payroll, Bale, or category records, and does not fabricate information for existing records. An attendance upsert that updates an existing row retains the original observation. If the source row's worker changes, the old observation is not displayed for the new worker. Entry-time craft is **not proof of craft on the attendance or payroll date**: backfilled or late-entered records can reflect a later label. A voucher observation represents draft creation, not necessarily approval/payment time. UI explicitly says so. Earlier records with no observation show the current craft labeled as such, not as historical fact. Category events remain a separate history; users must review original evidence for corrections.

Two bounded private-evidence tables link source and worker IDs and the observed label/time; RLS allows authenticated SELECT only when the parent attendance/payroll row is visible under its own RLS and still identifies the same worker. Authenticated clients cannot change observations, and anon/service cannot read or write them directly. Security-definer triggers record the craft, and row locks serialize observation versus a category rename. Trigger failure rolls back the source insert, and source FKs intentionally restrict deletion; this affects privileged cleanup as well as clients. Owners can bypass guards, and account/backup retention still requires review. Existing JSON history and payslip responses gain optional fields without changing signatures or prior fields. Attendance search matches both current and entry-time craft. A client using an older backend handles missing fields as unknown.

Synthetic tests cover historical/unknown labels, rename, upsert, source identity changes, RLS, immutable evidence, installation rollback, UI parsing and a weekly payroll/Bale payment-recording workflow. PostgreSQL CI includes concurrent rename versus attendance/voucher insertion. These do not prove every legacy/service writer, hosted Auth/PostgREST, all trigger interactions, full lock ordering or print/device behavior. The added inserts and restrictive FKs are an operational change: inspect source grants, existing triggers, row counts, cleanup procedures and function fingerprints; use a pinned artifact and transaction with rollback rehearsal before any installation. Do not infer actual payments or real historical truth from the tests.
