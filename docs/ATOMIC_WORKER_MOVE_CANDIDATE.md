# Atomic worker move — experimental, uninstalled

The currently installed guarded assignment supports removing a worker from one site and assigning them to another in **separate** actions. If the second action fails, the person can remain unassigned. That process does not create durable assignment history on the hosted development database. It does not alter paid payroll, attendance or Bale.

`supabase/drafts/atomic_worker_move.sql` is a separate candidate that requires the uninstalled `project_assignment_history.sql` and the reviewed guarded writer. An authenticated, assured Founder selects one current active **regular** worker, source site and destination. The function checks that the source is the only current active assignment, locks the actor, sites and worker, turns off the source and turns on the destination in the same transaction, and records an operation ID. The history trigger records an unassignment and assignment with the Founder actor. A failure in the second step rolls back both changes and both events. It does not change attendance, finance, pay, project access or Supervisor site assignments. It does not create historical intervals or infer prior moves; the history baseline is only an observation at installation. Source/destination are current membership, not a future or backdated assignment.

A default-off Founder project-team control requires **both** `NEXT_PUBLIC_ASSIGNMENT_HISTORY_PREVIEW` and `NEXT_PUBLIC_ATOMIC_WORKER_MOVE_PREVIEW`. It presents worker and destination and an acknowledgment, persists the request in session storage before sending and retries the same request ID on ambiguous outcomes. Request results are matched against the exact actor-scoped input. A replay acknowledges the original event even if the worker subsequently moved again; it does not prove current site membership. The Founder must refresh and inspect both teams and history. Storage unavailable or malformed blocks new moves. Stopping a retry does not undo anything and cannot prove an in-flight request finished. Lost/cleared storage, other browser tabs, actor changes and privileged/direct assignment writers remain operational concerns. The flag and UI are not authorization.

PGlite exercises authorization, exact retry after a later move, stale source, disabled history trigger and destination-history failure rollback. Disposable PostgreSQL 17 checks competing moves, identical retries, Founder demotion and the former-site Supervisor attendance guard racing a move, along with separate history/archive cases. In the rollback-only synthetic finance rehearsal the history, move and attendance guard are installed separately from the generated chain: a paid voucher and its site allocation remain unchanged after a move, while the old site's Supervisor write is denied and the new site's write succeeds. The fixture is synthetic, not hosted Auth/PostgREST, all client versions, worker removal guards and constraints, all delete/assignment paths, or a load/deadlock proof. The two history events are ordered for display and pagination by timestamps/UUID, not a globally proven causal timeline. In particular, equal timestamps are broken by random UUID and can display the destination assignment before the source unassignment; do not reconstruct causal order from tied events. A reliable causal sequence or paired-operation reference needs a reviewed design before history can be treated as a complete timeline. Request and history tables add project/worker delete restrictions; retained actors and operations have lifecycle, audit and recovery implications. Session assurance, account revocation beyond role changes, default privileges, multi-project lock ordering, restore/service-role writers, existing triggers, legacy clients, project status policy and complete target catalog must be reviewed before installation. If the assignment-history trigger is unavailable, new moves fail closed; an exact already-recorded replay may still return its original confirmation. The function is not bundled with the finance rehearsal or installed anywhere. No hosted data was changed. Do not enable flags or deploy this as a completed cutover.
