## What is prepared

- The earlier draft experimented with coordinated automatic and manual paths, but those paths are no longer wired to the manual endpoints or cron entry point. Their staged helpers and SQL are retained for possible future review, not active sending. Existing manual sends have their original behavior and limitations; they do not acquire the staged shared-contact lock.
- In the paused experiment, the catch-up planner chooses the latest missed slot, excludes an activation day at/after 8 a.m. Manila, respects pauses and requires a 24-hour gap since the most recent recorded contact for that channel. History considers the normalized destination across clients/invoices as well as client-wide SMS and invoice history. Some old records without a trustworthy destination can conservatively block unrelated reminders. Both channels can send for the same slot. A bounded cursor gives later invoices a turn over repeated cron calls. Slots cancelled before provider I/O can be reconsidered; accepted, rejected or unconfirmed slots remain claimed.
- The paused experiment includes a Founder-only review UI/API for new and older ambiguous records with evidence and an explicit confirmation that no sender is still running. The database cannot prove either assertion. A wrong decision can cause a duplicate. An accepted legacy review uses review time conservatively for the cooldown; original records are not altered. A later status change makes the old review stale.
- The default-off Supervisor deactivation UI/API uses a database restriction, preserved profile/history and separate Auth ban, with a read/retry flow when Auth is unconfirmed. `TEAM_DEACTIVATION_ENABLED` must remain off until every bypass path and hosted behavior are reviewed. Profile edits and promotion of blocked accounts are prevented. In-flight requests, existing signed URLs and copied data cannot be recalled. Reactivation is not implemented.

## Important limitations before rollout

1. **All deployments must participate.** Stop and drain any old cron, open deployments and in-flight manual senders before turning coordination on. Old deployments can bypass new locks. Don't simply flip an environment variable. Review rollback too: switching coordination off while a new sender is running can bypass its lock. The same applies to the team-access flag and old service-role routes. Worker registration is guarded by a staged RPC only in the new deactivation-enabled path; already-running calls and older deployments remain a risk.
2. **No lock protects changes after the final check. Matching the prepared destination to its reserved contact closes a common mismatch but is not a transaction with the provider.** Changes to invoice, contact, template or settings can race the provider request. Once a request starts, it cannot be recalled. A crashed sender or provider-uncertain result blocks until evidence-based review. A lost response after a successful database completion can instead release the lock while leaving the caller unsure; inspect recorded status before any manual retry. Invoice deletion is blocked while an attempt is active/unconfirmed; settled attempts, slots and reviews retain invoice identifiers. Review the deletion error shown to the Founder before deployment.
3. **History is incomplete outside the app.** The earlier experiment coordinated client-only SMS and associated it with the client in new logs; current manual sends do not use that path. Unlinked legacy SMS is conservatively considered for every client because attribution can be lost after phone changes/deletion; this can pause unrelated reminders until reviewed. External calls, unsaved historical attempts and provider-side activity cannot be inferred. Shared normalized contacts were coordinated in that experimental path (not in current manual sends), but provider-specific aliases (such as plus addressing), unrecorded historic destinations and external sends cannot be reliably matched. The separate email/SMS provider-test endpoints and staff welcome emails do not use reminder locks; review how they are used before activation, and never test against a client contact while senders are active.
4. **Scheduler is not configured.** Read-only Vercel metadata on 2026-11-07 identifies this project as Hobby and shows no legacy cron definitions; external or beta Schedules are not established by that metadata. [Official legacy cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing) are once daily with up to 59 minutes variation. [Vercel Schedules beta](https://vercel.com/docs/schedules/limits) documents Hobby intervals down to 15 minutes with 15-minute jitter and 5,000 runs per billing period shared across the team; excess runs are skipped. A 15-minute schedule during the Manila window is a possible free candidate, not a verified account capability or a promise of delivery. Confirm eligibility, usage headroom, deployment behavior (including previews), CRON_SECRET authentication, missed runs and duration before rollout. No schedule was created. A daily scheduler can delay catch-up when consecutive runs fall less than 24 hours apart.
5. **Team security and Auth need hosted verification.** On 2026-11-07 read-only metadata showed the expected four enabled user triggers, including the statement-level Founder mutation lock and `old_user_rows` update trigger. Existing authenticated table assurance policies and Founder Storage policies were inspected; the users self-profile bootstrap is an intentional exception. Re-review all exposed functions, grants, RLS, buckets, service-role paths and changes since then. Simulated Auth tests do not prove real Supabase ban timestamps, recovery, token invalidation, provider behavior or mobile/hosted workflows.
6. **No automatic rollout.** Confirm hosting schema/version and any installations that independently applied the old coordination file before using staged SQL. Drain traffic; take an appropriate backup; independently review and test against an isolated environment; and obtain separate approval before hosted changes or real tests. Do not run the whole migration queue against hosted Supabase.
