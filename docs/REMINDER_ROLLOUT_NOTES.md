# Reminder and team-access rollout notes

**Draft only; not ready to merge, deploy or activate.** The database still forces the Founder reminder master OFF. No staged SQL has been applied to the hosted project. Keep automatic sending off and do not send real messages or deactivate real accounts without separate approval. General cleanup is excluded.

## What is prepared

- The coordinated cron path, default-off manual email/SMS paths and review API are gated by `REMINDER_COORDINATION_ENABLED`. They use invoice/channel reservations; SMS additionally uses a client-wide reservation, so a client-only SMS and an invoice SMS for the same client cannot overlap. Email and SMS remain independent. The legacy cron is not used while coordinated mode is on.
- The catch-up planner chooses the latest missed slot, excludes an activation day at/after 8 a.m. Manila, respects pauses and requires a 24-hour gap since the most recent recorded contact for that channel. SMS history is conservatively client-wide; email history is invoice-specific. Both channels can send for the same slot. A bounded cursor gives later invoices a turn over repeated cron calls. Slots cancelled before provider I/O can be reconsidered; accepted, rejected or unconfirmed slots remain claimed.
- New and older ambiguous records have a Founder-only review UI/API with evidence and an explicit confirmation that no sender is still running. The database cannot prove either assertion. A wrong decision can cause a duplicate. An accepted legacy review uses review time conservatively for the cooldown; original records are not altered. A later status change makes the old review stale.
- The default-off Supervisor deactivation UI/API uses a database restriction, preserved profile/history and separate Auth ban, with a read/retry flow when Auth is unconfirmed. `TEAM_DEACTIVATION_ENABLED` must remain off until every bypass path and hosted behavior are reviewed. Profile edits and promotion of blocked accounts are prevented. In-flight requests, existing signed URLs and copied data cannot be recalled. Reactivation is not implemented.

## Important limitations before rollout

1. **All deployments must participate.** Stop and drain any old cron, open deployments and in-flight manual senders before turning coordination on. Old deployments can bypass new locks. Don't simply flip an environment variable. Review rollback too: switching coordination off while a new sender is running can bypass its lock. The same applies to the team-access flag and old service-role routes. Worker registration is guarded by a staged RPC only in the new deactivation-enabled path; already-running calls and older deployments remain a risk.
2. **No lock protects changes after the final check.** Changes to invoice, contact, template or settings can race the provider request. Once a request starts, it cannot be recalled. A crashed sender or uncertain result blocks until evidence-based review. Invoice deletion is blocked while an attempt is active/unconfirmed; settled attempts, slots and reviews retain invoice identifiers. Review the deletion error shown to the Founder before deployment.
3. **History is incomplete outside the app.** SMS to a client without an invoice is now coordinated and associated with that client in new logs. Unlinked legacy SMS is conservatively considered for every client because attribution can be lost after phone changes/deletion; this can pause unrelated reminders until reviewed. External calls, unsaved historical attempts and provider-side activity cannot be inferred. Different client records sharing a phone number and different invoices sharing an email address do not currently share a contact-wide lock or cooldown. Resolve or explicitly accept these limitations before automatic sending.
4. **Scheduler is unverified.** Vercel metadata on 2026-11-06 had no configured cron definitions; an external scheduler is unknown. No scheduler has been created here. A free daily scheduler may run only once per day and with timing variation, so a bounded batch can need multiple days to cover a large queue; a 24-hour cooldown can also defer a slot when consecutive daily runs are less than 24 hours apart. Choose and verify a free schedule/frequency and function duration before rollout; don't assume an endpoint schedules itself.
5. **Team security and Auth need hosted verification.** On 2026-11-07 read-only metadata showed the expected four enabled user triggers, including the statement-level Founder mutation lock and `old_user_rows` update trigger. Existing authenticated table assurance policies and Founder Storage policies were inspected; the users self-profile bootstrap is an intentional exception. Re-review all exposed functions, grants, RLS, buckets, service-role paths and changes since then. Simulated Auth tests do not prove real Supabase ban timestamps, recovery, token invalidation, provider behavior or mobile/hosted workflows.
6. **No automatic rollout.** Confirm hosting schema/version and any installations that independently applied the old coordination file before using staged SQL. Drain traffic; take an appropriate backup; independently review and test against an isolated environment; and obtain separate approval before hosted changes or real tests. Do not run the whole migration queue against hosted Supabase.
