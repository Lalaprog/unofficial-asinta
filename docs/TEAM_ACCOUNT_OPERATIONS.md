# Team account operations and recovery

Team account creation, editing and removal span separate Supabase Auth and database requests. They are **not a transaction**. A network timeout or later-step failure can leave some changes applied even when the UI cannot confirm success. Do not blindly repeat an unconfirmed action.

- Have only one Founder manage team roles or remove accounts at a time. The existing last-Founder check is a read followed by later writes; simultaneous demotions/removals are not serialized and can race. Do not claim this check protects against concurrent administration. A database-level concurrency control and multi-session test are still needed.
- After an unconfirmed creation, inspect both Supabase Auth and the BALE user profile before attempting another create. An Auth account may exist without a profile, or a profile may need cleanup. Verify the supervisor's project assignments and worker/payroll roster separately. Avoid sending credentials until the correct account and password are confirmed.
- After an unconfirmed update, check the BALE profile, Auth metadata/password-reset state, project assignments, worker/payroll rate and audit log. Never distribute a proposed password when the Auth reset was not confirmed. A lost response does not prove the password was unchanged. Use a new verified reset if necessary.
- Removal first clears some references and assignments, then removes the BALE profile, then requests Auth removal. Attendance and expense rows remain but their user attribution is cleared; payroll history remains. A failed step can leave prior cleanup applied. If profile removal succeeded but Auth removal was unconfirmed, the account no longer appears in Team Accounts; a privileged administrator must inspect Supabase Auth and clean up any remaining authentication account. Do not claim login/session revocation until verified. Existing access may persist in other services or sessions; check provider behavior and relevant permissions.
- If audit writing fails, the operation may still have completed. Reconcile the account state and record the incident through the organization's approved audit procedure. No temporary password belongs in the audit log.
- Test with disposable staging accounts first, including failures in each step and real Auth behavior. Inspect legacy accounts for incomplete prior operations. These safeguards report partial outcomes; they do not make the workflow atomic or fix historical inconsistencies.
