# Original-period project-cost correction evidence — draft only

**Correction-attribution evidence and the separate corrected inventory, preview and review ledger are installed in the development database only. Their UI is disabled by default; existing project totals are unchanged.** The installed review can calculate a separate incomplete total for supported original-site corrections, but cross-site incoming cases remain unsupported. This is not completion of historical/correction reconciliation or approval for real use. Do not rerun installed SQL or enable the workflow without coordinated release verification and a recovery plan.

## Model and boundaries

- A resolved paid **worker** voucher case or external-worker paid-period case may have a separately reviewed signed **gross cost effect**. Its net settlement difference is not automatically a gross cost. A deduction-only correction may have zero gross effect, and `no_transfer` does not itself imply zero or nonzero cost. Supervisor payroll is excluded from project cost.
- A human would assert the complete signed site split and a note, based on original records and all cases. The sum of site effects must equal the declared gross effect; site entries may be positive or negative. A zero total may be an empty split (no gross cost change) or a balanced reallocation between projects. Cases can still duplicate one another or overlap expenses and historical entries: this draft does not detect or resolve those risks.
- Each per-case revision **replaces the entire prior split**, rather than adding a new increment. The latest revision's site entries can be queried separately; historical revisions and exact case snapshot remain immutable. A site removed by a later revision must not reappear from an older revision. Existing saved cost reviews and their totals are unchanged, do not include these assertions, and cannot be treated as final costs. Site lookup omits zero/empty splits; the per-case lookup retains them.
- The database candidate requires Founder role and session assurance, restricts table/helper access, compares current original evidence, requires explicit acknowledgement and a resolved case, checks centavo precision and project IDs, snapshots all known cases for the source period, blocks new evidence while any is pending, and protects against stale revisions and ambiguous exact retries with immutable request IDs and advisory locks. External case writers share a global lock order; voucher case writers serialize through the worker and voucher. New or resolved sibling cases make prior evidence stale, but do not prove duplicates or overlaps are absent. It records no payment, transfer, payroll mutation, expense or accounting posting. A settlement assertion is not proof that money moved.
- A separately gated Founder interface can review and replace a full split against the exact resolved case, including no-transfer cases, with an acknowledgement and centavo-exact validation. A project page can separately display latest nonzero site evidence. Neither display includes these changes in a saved or scratch total. The gate `NEXT_PUBLIC_PROJECT_COST_CORRECTION_PREVIEW` is false by default and is not enabled by the development-finance cutover flag. The UI requires matching Founder identity and required session assurance; database checks remain authoritative.
- For an uncertain write the interface stores its exact request, case snapshot, split and note in sessionStorage scoped to actor and case, and retries only those details. The correction, original-voucher case and original-period assertion-case interfaces now refuse to recreate a missing retry record or clear a record that differs from the one reviewed for stopping; they recheck before clearing. Late responses after a scope change do not clear the new scope's retry. This data is sensitive to same-origin scripts and can be lost on browser/tab changes; an absent result does not prove failure. Stopping a retry neither cancels nor reverses it. These tab-local checks are not atomic cross-tab locks or protection against same-origin scripts. Changes to the surrounding case or loss of assurance fail closed.
- Synthetic PGlite tests cover actual external case integration and positive, negative, zero, reallocated and replacement splits, role/assurance denial, stale requests, rollback, immutable evidence and drift. An opt-in PostgreSQL 17 race suite was added to CI; results must be checked on the relevant commit. These tests do not prove hosted Auth/Storage/browser behavior or cover every legacy/privileged writer.

## Correction inventory candidate

`supabase/drafts/project_cost_correction_inventory.sql` is a separate development-installed read-only component that puts bounded combined source evidence and correction cases into one statement snapshot. It finds voucher cases for paid allocations in the base snapshot, external-worker cases for historical attributions in the combined snapshot, and cases whose latest reviewed split explicitly includes this project even when the original is absent from the snapshot. It deduplicates the references and looks up the full latest correction evidence for each case. An absent review is represented by `null`, not zero; a reviewed complete split that omits this site has site amount `0.00`, with the case freshness and sibling evidence still visible. A stale review or unresolved sibling is **not** an approval to use that amount. `source_in_snapshot` only means the original source is present in the bounded snapshot, not that a human included it in a saved review or that it is not a duplicate. The query caps case count and output size and fails rather than returning a partial inventory.

This inventory deliberately writes nothing and does not change old or new saved-review totals. It cannot discover every unattributed original or case with no site evidence, prove records complete or money paid, resolve duplicates, decide whether the original was included, or establish that independently entered sibling case effects do not overlap. The synthetic tests exercise missing versus explicit zero, signed corrections, replacement/removal, sibling drift, source inconsistency, bounds and access; the PostgreSQL 17 full-chain rehearsal passed on commit `9b2f5ef`.

## Corrected preview candidate

`supabase/drafts/project_cost_corrected_preview.sql` is a development-installed read-only component, not a saved review or accounting posting. It compares a complete inventory with a fresh statement snapshot (ignoring capture time only) and requires explicit decisions for every returned expense, historical original and correction, including documented reasons for all exclusions and for including a correction. It sums gross worker allocations and included historical gross once, then adds the signed site gross effects of included corrections, with excluded-case count exposed and the result always labeled incomplete. An excluded case is a documented omission, not an assertion that its effect is zero.

The server refuses included corrections without a current reviewed split, a resolved source and siblings, and an original included in this site's bounded review. It rejects historical voucher overlap, duplicate identities, missing case signals and a combined correction that would make the original site cost negative. Multiple included cases for one original now require a separate human assertion bound to the exact sorted case IDs, a specific explanation and an explicit statement that their gross effects are distinct and do not overlap; the saved review retains that assertion. The UI resets the assertion when the decisions change. The server and client independently check the sum for the original site; neither can prove that the human assertion is true or that all cases and sources are present. Reallocation into a site without an included original remains blocked and needs separate reconciliation. Exact human decisions can still be wrong, and cases with no discoverable site link or unrecorded expenses can be missing. A matching snapshot is not proof of completeness, payment, or future freshness. The calculation does not itself persist decisions or prevent a source changing immediately afterward.

Synthetic database tests cover signed amounts, exclusions, acknowledgement, exact evidence, reasons, sibling status, missing or stale attribution, source linkage, case-signal mismatches, overlap, duplicate-source decisions, negative original cost and access. The PostgreSQL 17 full-chain rehearsal passed for this preview on commit `f438191`.

## Separate corrected-review ledger candidate

`supabase/drafts/project_cost_corrected_review_ledger.sql` is installed on development. A separately gated UI candidate is in the working branch but is **disabled by default** and must not be enabled until its matching backend and release checks are complete. The ledger adds a separate immutable revision sequence rather than modifying the already-installed experimental reviews or their historical totals. A Founder with required assurance submits an acknowledged inventory, explicit choices and note. The server captures and checks its own evidence, recalculates with the corrected preview, serializes request and project revisions, and supports exact retry without a second row. Different details with the same request ID fail. The saved result remains explicitly incomplete and is not a payment or posting. A review read compares current bounded evidence and reports `matches`, `changed`, or `unavailable` at the read snapshot; `matches` is not completeness, a lock, or proof of future freshness. Exact replay reports the recorded revision even when later evidence changes; inspect its freshness separately.

This draft uses advisory locks for request/revision ordering and locks the Founder row; it does **not** lock every source writer. Source evidence can change between the final preview check and commit or immediately afterwards. ## Incoming cross-site project preview (uninstalled)

The original site amounts and correction effects must match the full split. The destination must have no original allocation and its incoming effect must be positive. A missing, stale, excluded, superseded or inconsistent source review blocks the context rather than assuming inclusion. These are human decisions within bounded data, not proof of payment or complete accounting.

`project_cost_cross_site_corrected_preview.sql` then validates an exact current context for each included incoming case, runs the existing destination preview with those incoming cases temporarily excluded, and adds only their validated positive effects to the incomplete result. It returns the incoming subtotal and count separately. All ordinary expense, historical and correction decisions and the destination snapshot still pass the existing preview's checks; extra or missing source contexts fail. Excluding an incoming case remains possible and requires no source context. Both new functions are **uninstalled and not connected to the UI or the existing saved ledger**; the separate cross-site ledger candidate below uses them. The existing corrected preview remains unchanged and continues to reject unlinked inclusions. They do not post or save a project cost and do not mutate payroll. Synthetic PGlite tests cover saved source decisions, missing/stale/excluded evidence, changed amounts, exact context and role/assurance checks. A real PostgreSQL synthetic finance-chain test now exercises source-review recording and an incoming destination preview; check its CI outcome before relying on it.

This preview supports exactly one original-period case per incoming source and requires source-site reviews first. It does not ensure every destination has an included review, establish that historical records or expenses are complete, lock source writers, or prevent a new source revision after the statement snapshot. Do not label the preview a final or posted project cost.

`project_cost_cross_site_review_ledger.sql` is a separate **uninstalled** durable-review candidate. It does not change existing review histories or post costs. PGlite tests use stub inventory/preview readers and cover replay, immutable rows, changed source context and permissions. A real PostgreSQL synthetic chain now also saves and replays a destination review, supersedes the source review, and checks freshness; check CI for the relevant commit. The cross-site ledger has no UI, client-side independent amount verification or exact browser retry yet, and is not in the held deployment bundle. Multi-case cross-site handling, writer/concurrency review, hosted rollback and release checks remain necessary.
