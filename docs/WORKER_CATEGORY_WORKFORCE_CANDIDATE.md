# Worker categories and workforce — coordinated candidate

**Installed on the development database only; not a production release.** This builds on the independent Founder category catalog; both category SQL files and both preview switches are required. Further installations require client and backend paths to be reviewed together. Old clients with free-text crafts will be refused for newly created/changed regular workers after installation. Supervisor account synchronization still uses its linked UUID and `Site Supervisor` designation; category labels never grant account roles.

The upgrade imports current regular-worker craft labels and the nine labels already in the registration form as configuration, attributes the baseline to the one existing Founder, and maps workers to durable category IDs. It fails rather than guessing on multiple Founders, invalid or Supervisor-like legacy regular-worker labels, unsupported catalog size or name collisions. Existing workers and financial records are not deleted. Only authenticated, assured Founders can add, rename, archive or restore categories; both Founders and Supervisors can read active names for registration. The database validates active names on regular-worker creation and craft changes, including service-role registration; an archived category remains on existing workers but cannot be selected for a new worker. Rename updates current worker position text for existing consumers, while immutable events retain the old and new category names. It can invalidate source-bound drafts; those need refresh/review. Paid vouchers are not rewritten. **Some old history screens join current worker position rather than a historical snapshot**, so they may display a renamed label; category event history is not a substitute for historical per-record position snapshots.

Roll Call and Workforce group and filter the workers actually present by their distinct current category labels (including archived labels); a vanished filter resets to all. The Workforce and project registration forms use the active catalog only when both `NEXT_PUBLIC_WORKER_CATEGORY_PREVIEW` and `NEXT_PUBLIC_WORKER_CATEGORY_WORKFORCE_PREVIEW` are true. A failed category read disables new category selection; the backend is still the final authority. UI options can become stale across tabs, so the database rechecks the category. The Founder manager warns about rename effects and audit history, and category changes refresh the active choices in the same tab. Direct database owners can bypass permissions and triggers; operational access and recovery still matter. Existing account provisioning/upsert, inherited grants, old sites, client/schema versions and race behavior require special review before installation.

Synthetic PGlite and UI tests exercise legacy mapping, category rename/archive, restrictions, linked Supervisor provisioning, payroll status preservation, category history, audit failure rollback and unavailable catalogs. A dedicated PostgreSQL 17 race test and CI step covers registration racing rename/archive. Those are not proof of real Auth/PostgREST behavior, all existing worker integrations, populated historical data, every lock order, or UI accessibility. Before a development rollout, use a pinned artifact and transactional hosted preflight, identify all workers/positions and clients, ensure the matching preview is ready, review unavoidable compatibility changes and confirm role/service privileges after installation. Do not run stale bundles or blindly replay SQL. Independently configured failure alerts and tested recovery remain prerequisites to real use.

### Reversible removal compatibility repair

The category worker trigger initially caused the existing strict removal schema guard to reject all worker archives and restores, safely returning `WORKER_REMOVAL_SCHEMA_REVIEW_REQUIRED` without changing workers. Development migration `20261114014631_development_worker_removal_category_compatibility` repairs this interaction. It accepts only the expected enabled category-binding and assignment-history triggers with the reviewed shape, rejects other active triggers and locks both tables against concurrent trigger DDL for the duration of an archive. Existing Founder/service-role authorization and audit behavior remain unchanged. The hosted repair was pinned and hash-checked, with pre-install function fingerprints and a rolled-back missing-worker rehearsal; no worker was inserted or removed. Post-install: zero workers, nine categories, two Auth users and profiles, no temporary HTTP extension; service-only removal ACL unchanged. Synthetic combined tests exercised archive/restore, assignment/audit evidence and preserved attendance/payroll; PostgreSQL 17 CI tested concurrent disabling of the category trigger. A populated hosted removal or real browser flow has not been tested and was not performed. Scope is reversible workforce removal; it does not remove a Supervisor login.
