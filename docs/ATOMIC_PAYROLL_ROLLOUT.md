# Atomic payroll payment rollout

The `20261102000000_atomic_payroll_payments.sql` migration changes live financial write permissions. **Do not deploy it casually or assume past payments are repaired.** It does not move money; staff must still pay the worker before marking a voucher paid. It does not change, reconstruct, or reconcile existing ledgers.

## Before production

1. Back up the database and prepare a staging copy without exposing real personal data. Reconcile historical paid vouchers and manual deductions against actual disbursements, advance balances and audit history. The old flow could leave partial or duplicate deductions, and an already-paid voucher is deliberately treated as a no-op on retry; it will not be repaired automatically. Escalate discrepancies for controlled accounting review, not blind replay.
2. Schedule a maintenance window. Stop all payroll approvals/payments and manual Bale changes, including other integrations, before deployment; finish or reconcile any in-flight transactions. Inventory external clients that directly update `payroll.status` or `advances`: these updates will be denied after migration. No legacy client may be used for financial writes after rollout.
3. On staging, apply the migration after the earlier schema, security and Bale migrations (or the generated `upgrade-hardening.sql` when appropriate). Deploy the matching application, reload PostgREST's schema cache if necessary, force all users to refresh/reopen their sessions, and run `supabase/apply/verify-live.sql`. A PASS checks object/privilege presence, not behavior or correctness.
4. As a Founder, create draft test vouchers and advances. Approve, actually simulate paying, then mark a voucher paid; check exact deductions and audit snapshots. Repeat the payment RPC with the same voucher and confirm no second deduction or audit entry. Test insufficient balance, a failed audit insert, manual deduction, finalized recalculation, two simultaneous same-worker operations, and a stale old client. As a supervisor/anonymous user verify all three RPCs are denied. Test realistic multi-session concurrency on hosted staging: the local PostgreSQL tests use a single PGlite connection and cannot establish concurrency behavior.
5. Repeat the coordinated pause, migration, app deploy, schema-cache refresh, forced browser refresh and verification in production only after staging and reconciliation are accepted. Monitor errors before resuming work. The new app fails closed if the migration or RPC is missing; old clients cannot update the protected columns after the migration. During deployment neither version should perform payroll/Bale writes.

## Operational notes and recovery

- The payment RPC locks the worker, voucher and current active/partially deducted advances, consumes oldest advances first, and commits deductions, paid status and their audit entries together. A current balance below the approved voucher's deduction blocks the entire transaction. Approved/paid voucher financial fields are protected from recalculation. There is currently no UI to revise an approved voucher: investigate and resolve the discrepancy through a controlled, audited administrative procedure before retrying; do not invent an advance or mark it paid outside the RPC.
- A lost response can mean a transaction committed even though the UI could not confirm it. Refresh and inspect both ledgers and audit history. Retrying **the same payroll voucher payment** is idempotent after this migration. Manual deductions are not idempotent: never blindly retry an unconfirmed manual deduction; verify the balance and audit first. A manual deduction can legitimately make a previously approved voucher's Bale deduction unaffordable.
- A database transaction failure rolls back its deductions, status and audit entries. A payment retry on a voucher already marked paid before this migration also does nothing, including for a historically inconsistent voucher.
- If rollout must be stopped, keep financial writes paused. Restore the application and database from the tested recovery plan or deploy a forward fix, with accounting review of any operations committed since backup. Simply re-granting direct UPDATE or rolling back the application reintroduces the original partial-write/double-deduction risk. Do not resume the old workflow until a separately reviewed safe plan is in place. The SQL bundle's transaction only rolls back a migration that fails before commit; it is not a post-deployment undo.
