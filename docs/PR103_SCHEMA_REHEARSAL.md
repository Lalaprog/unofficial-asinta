# PR #103 schema readiness — work in progress

## What is known

The merged web code has been promoted. The site-guard migration `20261113000004` was installed separately as hosted `20261112051533_pr103_bale_request_site_guard`; the other six `20261113000000`–`20261113000006` migrations remain absent. New screens relying on those missing migrations cannot load. Legacy payroll and Bale still use the old rules. Do not treat these features as a completed payroll release.

`supabase/preflight/pr103_readiness.sql` is a **read-only, partial catalog check**, not a deployment script. Before the site guard was installed, its check against the connected database returned: `app_private` present, no missing named relations/helpers, no conflicting named new tables/functions, and no explicit column ACLs on `advance_requests`. The guard function and four explicit INSERT column ACLs are now expected to be present; do not treat that pre-guard output as current. This is a point-in-time result and does not verify column types, function bodies, role membership, active requests, live clients, trigger side effects, identity data, hosted Auth/PostgREST or concurrency. It also cannot prove the schema is equivalent to a staging environment.

The database gives `anon`, `authenticated` and `service_role` broad default privileges on future public tables, functions and sequences created by `postgres`. The seven migrations explicitly restrict the new tables and functions; however the identity sequence for `attendance_time_details` would otherwise inherit direct client privileges. The follow-up `20261114000001_protect_time_detail_sequence.sql` revokes client access to that sequence, keeps existing service privileges, and fails rather than changing inherited role privileges silently. It has **not** been applied to the hosted database: the sequence does not yet exist there. Install it in the **same transaction** as the time-detail migration if a future release is approved, not as a delayed independent patch.

## Rollback-only local rehearsal helper

`scripts/build-pr103-rehearsal.mjs` generates an ordered **rollback-only** SQL script for an isolated disposable database that has the installed site guard. It checks the guard body, enabled trigger and selected INSERT ACLs; excludes the already-installed guard and paid-review RPC; runs the remaining six migrations with the time-detail sequence safeguard in the same transaction; checks selected RLS/grants; and ends in `ROLLBACK`. Inputs carry SHA-256 comments and a conservative transaction-control tripwire. `tests/pr102-migration-sequence.test.ts` exercises this exact generated SQL in PGlite, including a missing/disabled guard, a late function-name collision and rollback, preserved fixture records and a successful rollback. This helper is **not** a deployment script, a comprehensive ACL/catalog check, or a substitute for an isolated hosted-equivalent PostgreSQL rehearsal. Even rolled-back DDL can lock tables: **never run it against a shared database**. A fresh generated script needs manual review, including transaction boundaries, before use.

The manual GitHub migration workflow on this branch has been disabled and fails before accessing secrets or a database because its bundles and migration history are stale. This does not disable older revisions or direct/manual database access.

## Account-preservation assessment (read-only)

`supabase/preflight/account_access_integrity.sql` reports aggregate Auth/profile and project-supervisor linkage counts without returning IDs, names, emails or credentials. Tests exercise missing profiles, missing Auth identities, broken site links, incorrect linked roles and empty fixtures. It is a diagnostic only: no changes are made, and a clean result does not prove passwords, MFA, RLS, functional login or full schema compatibility. Account, profile, role, MFA and access settings must not be reset as a side effect of any proposed test-data cleanup.

The current connected development project's aggregate check returned two Auth identities and two matching application profiles (one Founder, one Supervisor); there were no orphaned identities or profiles. One Supervisor project link exists, with no missing project/profile or non-Supervisor linked role. This is a point-in-time structural observation, not a successful login test. A catalog foreign-key inspection also showed that Supervisor links reference both users and projects, and that Auth identities and MFA factors depend on Auth users. Deleting projects can affect Supervisor access; deleting Auth users is not an account-preserving reset. Inventory additional dependencies, settings, triggers and Storage before proposing any cleanup. No cleanup or schema writes were made during this assessment.

A repeat of the partial PR #103 catalog preflight found all named prerequisite relations/helpers present, the four expected new relations and all named new functions absent, and the installed site guard enabled with the previously recorded body hash. This does not prove column types, policies, full function behavior or migration safety. The recovery deployment is still the most recent READY production deployment; GitHub main remains ahead of it. Keep incomplete panels off and preserve the running site while the schema and release are reconciled.
