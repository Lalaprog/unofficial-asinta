# Protected invoice payments: rollout and recovery

**Do not apply this migration to the live database without an agreed maintenance window and explicit approval.** It changes write permissions and prevents older browser tabs and direct integrations from changing invoice payment fields. It does not collect money or alter/reconcile historical invoices. The corresponding app requires the new RPC and fails closed if it is unavailable. There is no silent fallback to the old calculation.

## What changes

- A Founder records the receipt as before. The database locks the invoice, checks the total, paid amount and status the Founder saw, validates a positive amount with at most two decimal places against the current balance, and writes the balance, status, operation ID and before/after audit entry in one transaction. An audit or operation-ledger failure rolls the entire payment back.
- A changed invoice is rejected rather than silently applying a payment to a different balance. The Founder must check whether the other transaction recorded the same receipt before entering another payment. Different request IDs do **not** identify the same real-world receipt. No receipt/reference number is required today, so duplicates entered deliberately or from separate devices **after reviewing the updated balance** remain possible.
- A request ID makes retries of that exact request safe, including a lost response. The browser saves a pending attempt (invoice ID, amount, expected totals/status and request ID) in local storage before sending. An unconfirmed attempt is available under **Resolve payment**, even when the invoice now appears paid; retry uses exactly the saved details. Do not clear browser data, change browser profile/device, or use a private session until it is resolved. Local storage is device/profile/origin-specific, can be viewed by someone with access to the browser profile, and is not a shared receipt ledger. If unavailable, the app refuses to send. If the key is lost or the invoice is absent from the loaded list, stop and ask the administrator to inspect records before attempting a new payment. The audit trail contains invoice before/after snapshots; the operation ledger contains request IDs and amounts for new operations, not historical receipts. A missing operation in an ordinary read does not prove an in-flight request will not commit.
- Reminder setting changes no longer write status derived from the browser snapshot. Direct authenticated `UPDATE` of `amount`, `amount_paid`, or `status` is blocked, including for old clients; authenticated inserts cannot start with a nonzero payment or a paid/partially-paid status. Current invoice creation, reminder settings and other nonfinancial metadata writes remain supported. There is currently no in-app financial amount correction or invoice cancellation workflow; direct integrations that rely on those operations must be inventoried and a controlled audited replacement designed before rollout. Privileged database/service-role actions remain outside these guards and need separate operational controls. Existing deletion and other non-payment audit behavior are unchanged.
- Historical payments are **not** backfilled into the operation ledger or corrected. Deleting an invoice does not delete its new operation IDs, so a retry cannot recreate a payment. Invoice creation, deletion, and reminder audit writes remain separate from their mutations; this change only makes the **payment** audit atomic.

## Coordinate deployment

1. Inventory all clients and integrations that insert or update invoices, including service-role jobs and old browser tabs. Resolve compatibility for direct financial corrections/cancellations. Review historical records against actual receipts and investigate anomalies separately. Back up and have a tested recovery plan. A staging environment is a separate safe copy of the system for rehearsals; it may incur hosting cost and must not expose real personal data. If no staging environment exists, agree on an alternative safe rehearsal and its risks before production.
2. Pause invoice creation, payments, edits and integrations; reconcile in-flight/unconfirmed requests. Schedule downtime. Apply **only** `supabase/migrations/20261104000000_atomic_invoice_payments.sql` after confirming its prerequisites (`invoices`, reminder columns, `users`, `is_founder`, `audit_log`, and expected privileges) and the actual hosted schema. Do not blindly run `supabase db push` or the full upgrade bundle: the hosted migration history differs from the repository and other financial migrations may have unknown rollout status. Record the actual hosted migration version separately.
3. Deploy the matching app in the same window. Refresh the PostgREST schema cache if needed, force all users to reload, and ensure stale clients are no longer in use. Run `supabase/apply/verify-live.sql` and inspect any failures; a PASS checks object/grant presence, not transaction behavior, data quality, effective custom role inheritance, or the correct deployed app. Verify direct permissions and custom role/integration behavior explicitly. Do not resume invoice work until both sides are confirmed.
4. In an isolated test environment, test partial and full receipts, excessive/zero/third-decimal amounts, cancelled invoices, reminder toggles, non-Founder denial, and audit rollback. Test two sessions starting with the same balance: one succeeds, the other must review a stale result. Test simultaneous same-key retry and a lost response/reload; verify exactly one operation and one audit entry for that key. Also test old direct writes and unpaid invoice creation. Confirm on actual signed-in accounts/devices before trusting the production workflow. Do not perform destructive/audit-failure tests on live data.
5. Reopen work only after the responsible person approves the checks. Monitor errors and any remaining unconfirmed attempts. Never re-grant direct financial updates just to make an old client work.

## Recovery

For an unconfirmed payment, use **Resolve payment** on the same browser profile and retry the exact attempt once service is available. This can record the payment if the first request never committed; otherwise it returns the already-recorded result. If the saved attempt is unreadable, the browser data was lost, or a request mismatch occurs, stop: the administrator must inspect invoice totals, actual receipts, audit snapshots and operation IDs, including in-flight requests, before deciding on any new entry. A changed-invoice warning means that specific attempt did not record a payment, but another person's payment may be the same receipt.

If deployment must be halted, keep invoice financial work paused and use the tested recovery plan or a reviewed forward fix, accounting for any operations committed since backup. Reverting only the app or re-enabling direct updates restores the original race and non-atomic audit risks. Do not delete operation IDs while retries might exist. A transaction-wrapped migration rolls back a failed migration, not operations committed after deployment.

## Local multi-session test

`tests/invoice-payment-concurrency.test.ts` is opt-in and destructive to its fixture database. Point `INVOICE_PAYMENT_TEST_DATABASE_URL` only at a **new empty local** database named `asinta_test_*` and run `npx vitest run tests/invoice-payment-concurrency.test.ts --maxWorkers=1`. It deliberately blocks one session on another, checks same-key and different-key races, and tests a reminder/payment race. This is not a substitute for hosted, signed-in tests.
