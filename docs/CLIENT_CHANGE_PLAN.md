# Client change plan and deferred items

This is a working plan, not a statement that all features below have been delivered. The draft PR only includes the items explicitly described in its summary and must not be treated as a completed payroll, attendance, privacy or database rollout.

## Agreed rules for later implementation

- Workers: Sunday–Saturday period, normally paid on that Saturday. Supervisors: 1st–15th and 16th–last day of each month, normally paid on the period end. Manila dates; the schedule is not anchored to the launch date. The period helpers are not yet connected to payroll.
- Unmarked is not absent; the Founder may backfill recorded attendance. Warn when calculating an incomplete period. Historical paid records and Bale must not issue or deduct money again. Preserve the original paid record and resolve differences against the original period; never automatically carry them into another period.
- Regular hours and OT are separate; one day is eight regular hours. Requested OT is daily rate / 8 × OT hours; client should confirm applicable legal/payroll requirements before real use. Allowances submitted by a Supervisor require Founder approval; Founder can directly record them.
- Bale request and Founder approval Sunday–Tuesday; unapproved requests rejected after Tuesday. Wednesday release recorded by Founder or authorized Supervisor; full released amount for the period deducted from Saturday payroll. No new request/approval Wednesday–Saturday. An excess deduction needs Founder review, never silent negative pay.
- One general attendance record per Supervisor per day. Founder can approve even if project attendance is missing; show indicators for assigned projects. Normal leave requires two calendar days' notice in Philippine time; emergencies may be filed late, including past dates. Founder decides; approved leave is unpaid.
- Regular workers have one active project assignment; Supervisors may handle multiple sites. Restrict Supervisors' ordinary rosters to the selected authorized project; allow unassigned-worker discovery only when adding to an authorized project. Existing duplicates require review rather than silent changes. Founder manages worker categories.
- Project expenses include confirmed rentals and approved **and** paid worker payroll, without counting Bale twice. Determine worker cost attribution from the period's project work. Supervisor payroll remains a company cost, not a project cost for now.
- Founder-only expense creation and receipt uploads; multiple photos can be saved for later, with optional AI/manual processing. A photo alone is not an expense. Preserve existing records. The first batch does not change or certify current expense permissions.
- Tools need owned stock and site/depot allocations with over-allocation prevention, rental tracking and linked expenses. The project Workforce Logs and Attendance History calendars are in the draft; detailed regular/OT hours, allowance approval, leave, payroll reports and optional Supervisor profile photos still need implementation and testing. A read-only nine-up payslip layout is in the draft, but print readability still needs real browser/printer checks.

## Deferred after the defense

- Client-owned deployment: use a reviewed structure-only migration and verify security/configuration. Do not copy development business records or accounts. The existing fresh-install bundle must be verified and updated before use.

## Assignment rollout and outstanding privacy work

The draft adds a guarded single-project assignment path and available-worker lookup; it does not change existing duplicate assignments. Its migration must be applied and verified before the app using the new lookup is deployed. Supervisor exceptions use a worker UUID linked to a Supervisor account; unlinked legacy identities need review. The Supervisor workforce screen filters the selected project and the ordinary Roll Call response no longer includes available workers; the add flow requests those separately. The existing global worker-read policy and other workforce entry points are not yet redesigned, so these UI/API changes do not establish the requested Supervisor privacy boundary. Preserve scoped historical names, Supervisor identity safeguards, duplicate registration checks and existing drafts when changing database policies. Privileged service-role direct writes bypass the guarded assignment function; all app assignment entry points must use the guarded path. Do not infer live concurrency safety from the single-session database tests. The hosted migration history differs from the repository; do not blindly push migrations.


## Worker payslip batch (draft, not deployed)

The Founder can request an exact-period, read-only database snapshot of existing worker vouchers and print them in groups of nine per A4, or use the existing individual slip. All statuses are included and labeled; printing is not an approval or payment. Both layouts omit the logo and explicit rate, although pay figures can reveal an inferred rate. The slips intentionally omit site attribution because the existing vouchers do not hold a reliable historical site snapshot. The batch excludes accounts linked by UUID to Supervisor profiles and fails closed on duplicate vouchers, missing workers or obvious unlinked Supervisor identities (position/name). Those checks are heuristic and cannot establish the identity of every legacy profile; the Founder must review the list. The report shows existing voucher amounts, not the requested new payroll calculations, and does not create unpaid-day or OT calculations.

Migration `20261112000001_payslip_batch_snapshot.sql` is required before deploying the batch UI and is not applied to the hosted database. Check the hosted migration history before a controlled rollout; do not blindly push. The SQL uses caller RLS and Founder checks, with bounded output. Local database/component tests do not prove hosted permissions, print layout, privacy handling, or real-device readability. Test A4 print previews and actual pages with long names and larger amounts on supported browsers; use individual slips if nine-up is not legible or content overflows. Refresh the batch if vouchers change elsewhere.

The month view is shown on desktop; mobile has a seven-day strip with week navigation and expandable day details. A blank date is not called absent. Date/identity changes invalidate stale reads, failures are shown with retry, and a refresh is available. Counts represent entries, not attendance completeness; record pages may change as attendance is edited and are not a locked historical snapshot. Current schema only provides recorded hours; it does not yet split regular/OT. Founder editing/backfill remains in the existing Attendance History flow, not this project calendar.

## Recorded project expense history (draft, not deployed)

Project list cards and project detail now request Founder-only server totals for the projects present in the current project list, rather than summing the potentially truncated shared expense store. Detail pages provide a site-specific, keyset-paged recorded expense ledger, including older entries, with centavo display, explicit loading/error/retry and refresh. The summary is not silently replaced with zero on an error, and an invalid/stale response is discarded. The queries use caller RLS and `is_founder()`; they do not write expenses or change receipts, approval, payroll, Bale or rentals. The connected development database's relevant expense columns and Founder/MFA policies were checked read-only.

The amounts cover only existing `expenses` rows. Automatic inclusion of approved-and-paid payroll and confirmed rentals is **not implemented**, and separately recorded expenses should not be counted again when those integrations are designed. Totals and each page are separate database reads, not a locked historical snapshot; edits during browsing can change order/counts, so refresh when needed. The totals request is bounded to 2,000 IDs, and pages to 25 in the UI; errors require review rather than falling back to partial data.

Migration `20261112000003_project_expense_ledger.sql` is unapplied and must be reviewed before the app is deployed. Its index creation may briefly block writes and should be scheduled and verified against the actual hosted schema. Local RLS/assurance tests do not substitute for authenticated hosted tests or desktop/mobile usability checks. No hosted migration or data write was performed.

## Founder receipt photo inbox (draft, not deployed)

The Expenses page can save independent JPEG/PNG/WebP photos (up to 5 MB each) one at a time and page through them later. Only an explicit complete expense submission creates a ledger entry. A ready photo can be viewed, attached to a new manual entry, or explicitly scanned with AI when there is no unfinished or saved draft. Scanning sends the selected photo to Groq, is limited to 4 MB, verifies the downloaded bytes against the inbox digest, and reuses the existing storage path rather than uploading a second copy. The form is locked during the scan, with network timeouts; on ordinary failure the photo link remains for manual entry and must be checked; if the bytes no longer match, it is detached rather than silently used. Existing photos/drafts are not migrated or modified. The inbox keeps ready photos after use, so the Founder must avoid attaching the same receipt to duplicate expenses; no automatic consumed status or cross-tab exclusive reservation is claimed.

Saving first creates a pending record with a stable ID and digest, then uploads without overwrite and marks it ready only after the caller can see its private storage object. An interrupted upload can be retried with the same file while the page is open, or a pending record can be resumed by its original Founder selecting the same bytes. If creating the pending record has an ambiguous outcome, retry the same attempt or refresh and inspect the inbox before beginning again; if the page is closed before the pending record exists, the photo needs to be selected again. Failed or abandoned entries and objects are retained: there is no inbox deletion/cleanup, because photos may already be referenced elsewhere. This consumes storage and needs a future reviewed cleanup/retention design. The database does not independently verify the client-provided digest or prevent a privileged user from changing storage objects; it is a recovery guard, not proof of image authenticity.

Migration `20261112000004_receipt_photo_inbox.sql` is unapplied and depends on existing Founder/MFA helpers, `users`, and private receipts storage policies. Caller RLS and restrictive MFA guard metadata; existing Founder-only storage policies guard photos. The ready trigger checks storage object visibility with caller permissions. Browser tests and a simulated local database do not establish hosted Storage/API behavior, interrupted network recovery, actual permission configurations, or mobile usability. Verify authenticated Founder and Supervisor sessions and recovery on an isolated environment before deployment. No hosted migration, record, photo or other data was written in this batch.
