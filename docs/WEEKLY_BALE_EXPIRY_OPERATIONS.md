# Weekly Bale expiry: uninstalled operational candidate

**Not active.** No extension, scheduler, monitoring service, grant or job is installed by this draft. It is not a migration and must not be applied independently of the reviewed weekly Bale/finance cutover. Legacy requests are not swept. No message or money is sent by the runner; the existing in-app rejection notification and audit are written in the same transaction as rejection.

## Intended behavior

`supabase/drafts/weekly_bale_scheduler.sql` runs at most five 100-row worker batches in **one transaction** (500 total), uses a transaction advisory lock to avoid overlapping runs, and records success only after the whole batch succeeds. A once-per-minute job at all hours is the proposed cadence; it does not depend on local cron timezone. The worker decides eligibility with server time in Asia/Manila: Wednesday 00:00 onward for the marked weekly request. The schedule is not an exact deadline guarantee: outages, failed runs, paused projects, backlog or locks delay durable rejection. The read-side projected status blocks decisions after Tuesday even while a rejection is pending, provided the complete compatible weekly guards and UI are installed. `SKIP LOCKED` returning zero does **not** mean no work is due; the runner separately counts overdue marked requests, including rows another transaction has locked. Repeated committed runs drain backlog; 500 rows is a maximum, not a throughput guarantee. One malformed row can roll back a whole run and block progress until investigated.

The default-off Founder check is an on-demand observation, not automatic alerting. It shows success only if the last completed transaction is no more than three minutes old and the current due count is zero. This does not prove a job is configured, future execution, correct permissions, event delivery, or historical data completeness. An observation immediately goes stale; refresh it. It requires all of `NEXT_PUBLIC_FINANCE_FOUNDATION_PREVIEW`, `NEXT_PUBLIC_WEEKLY_BALE_RELEASE_PREVIEW`, and `NEXT_PUBLIC_WEEKLY_BALE_EXPIRY_HEALTH_PREVIEW` at build time; UI flags never authorize database operations. An operator must independently monitor job failures/heartbeat and follow up; no notification for scheduler failure is implemented.

## Before any activation

1. Finish finance/release integration and review all dependencies, existing data, audit, RLS, ownership, function bodies and privilege inheritance. Reconcile legacy pending/issued requests and separately recorded Bale rather than classifying them automatically. Verify recovery/restoration including Storage and Auth before real client data. Rehearse the complete cutover and rollback on an isolated, representative project; synthetic tests are not a hosted Auth/PostgREST or scheduler test.
2. Verify the provider supports `pg_cron`, job execution and a dedicated **database login** identity on the target project. As of the read-only development inspection `pg_cron` 1.6.4 was available but not installed; `cron.timezone` was GMT. That is not proof of installation privileges, identity, uptime, alerts, or behavior on a different project. Confirm database `cron.database_name`, connection/auth, `cron.use_background_workers` as applicable, job ownership, limits, UTC setting, logs/retention, paused-project behavior, and extension-upgrade impact. Use a reviewed least-privilege login with only `EXECUTE` on the runner; it must not be an API role, a user JWT session, an owner, or a role able to alter the runner or source tables. Test that identity in the isolated project first. The runner and worker are SECURITY DEFINER, so ownership and every reachable function/trigger must be trusted and reviewed, including inherited privileges. Do not expose runner execute to service_role or browser clients.
3. Coordinate installation, secure extension and cron metadata, grant only that tested operator identity execute, and ensure transaction isolation is read committed. Explicitly verify server settings and the job's actual database/user. Define alerting outside the app for missed heartbeat, overdue backlog, failures and project pause; assign an accountable person and escalation path. The Founder button is **not** a substitute. Verify run-history access/retention and make alerts independent of the failing project. Record costs and provider limits.
4. Schedule **once per minute, every day**, using `* * * * *` (identical in UTC and Manila); do not substitute a Tuesday-only schedule because missed runs require catch-up. The reviewed cron command should execute only `SELECT public.run_weekly_bale_expiry_job();`, with an appropriately bounded statement timeout set for the job connection. Check whether the provider records function return values or only SQL errors: `already_running` is not a new heartbeat. Inspect the exact resulting `cron.job` identity, active status, command and database; eliminate duplicate jobs. Do not embed credentials or service keys in commands or source control. Test missed-run catch-up and locked rows with approved synthetic data in isolation before production.
5. Only enable the UI on the compatible deployment after the RPC and permissions are verified. Confirm healthy/no backlog, inspect actual persisted rejections and matching system audit/in-app notifications, and test failure and alert escalation without real payments or external sends. Watch the first real boundary. Historical or external Bale remains subject to separate human reconciliation.

## Recovery, disabling, and rollback

- If heartbeat is missing/stale or due count is nonzero, inspect provider job/run history, paused status, database connectivity, locks and exact SQL error. Keep the decision guards active; do not bypass them or manually issue payments. Repair the cause, then allow independent job transactions to retry. Do not assume a zero processed count means a clear backlog.
- To stop further execution, an authorized operator disables/unschedules the **specific verified job ID**, waits for any already-running transaction to finish, and confirms no later runs. Revoke the dedicated identity's execute and disable the health UI. Preserve logs, audit and rejection/notification records. Disabling scheduling does not undo committed rejections. If already persisted decisions require correction, use a reviewed human reconciliation procedure; do not silently change financial history.
- Reverting database objects/guards must follow an integrated, tested rollback plan that preserves history and handles old clients. Do not drop columns, remove audit evidence, re-enable unsafe legacy flows, or uninstall a shared extension blindly. Determine compatibility and dependencies first. After downtime, resume the minute job only after verification; repeated runs catch up older marked requests.
