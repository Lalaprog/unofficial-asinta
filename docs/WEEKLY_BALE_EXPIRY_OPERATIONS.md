## Intended behavior

A disposable PostgreSQL 17 CI rehearsal at commit `2204a85` submitted 501 synthetic requests, held one row locked, and verified a 500-row run, the outstanding backlog signal, a zero-processed retry while locked, subsequent catch-up, notifications, system audit and no new advances. This exercised synthetic fixtures and direct job calls, not the hosted cron, hosted Auth/PostgREST, an actual outage or the independent alert service.

`supabase/drafts/weekly_bale_scheduler.sql` runs at most five 100-row worker batches in **one transaction** (500 total), uses a transaction advisory lock to avoid overlapping runs, and records success only after the whole batch succeeds. A once-per-minute job at all hours is the proposed cadence; it does not depend on local cron timezone. The worker decides eligibility with server time in Asia/Manila: Wednesday 00:00 onward for the marked weekly request. The schedule is not an exact deadline guarantee: outages, failed runs, paused projects, backlog or locks delay durable rejection. The read-side projected status blocks decisions after Tuesday even while a rejection is pending, provided the complete compatible weekly guards and UI are installed. `SKIP LOCKED` returning zero does **not** mean no work is due; the runner separately counts overdue marked requests, including rows another transaction has locked. Repeated committed runs drain backlog; 500 rows is a maximum, not a throughput guarantee. One malformed row can roll back a whole run and block progress until investigated.

Synthetic PostgreSQL tests also inject a failure on the second request in a batch: the first rejection, its notification, and the heartbeat all roll back, and a later run after repair rejects each request once. This exercises database transaction recovery, not a real cron installation, external alerts, production backup or full project restore.

The default-off Founder check is an on-demand observation, not automatic alerting. It shows success only if the last completed transaction is no more than three minutes old and the current due count is zero. This does not prove a job is configured, future execution, correct permissions, event delivery, or historical data completeness. An observation immediately goes stale; refresh it. It requires all of `NEXT_PUBLIC_FINANCE_FOUNDATION_PREVIEW`, `NEXT_PUBLIC_WEEKLY_WORKER_CUTOVER_PREVIEW`, and `NEXT_PUBLIC_WEEKLY_BALE_EXPIRY_HEALTH_PREVIEW` at build time; it remains visible even if the weekly write flags are incomplete. UI flags never authorize database operations. An operator must independently monitor job failures/heartbeat and follow up; no notification for scheduler failure is implemented.

## External monitoring probe (function installed; independent monitoring not active)

`supabase/drafts/weekly_bale_external_monitor.sql` adds a separate, read-only, single-boolean health function for an external monitor login; it reveals no request or worker details. It fails closed for a missing, stale or future heartbeat or any currently overdue marked request, including locked rows. It requires the matching scheduler and is not a standalone migration. It grants no login or access, schedules nothing and sends no alerts. API roles are explicitly denied and checked for inherited execute access.

`scripts/check-weekly-bale-expiry.mjs` is a one-shot probe for an independently operated monitor. It requires `BALE_MONITOR_DATABASE_URL` with `sslmode=verify-full` and `BALE_MONITOR_DATABASE_ROLE`; use an isolated secret store, never source control or logs. It verifies TLS certificates, checks the actual login and selected privileges, and returns exit 0 only for a healthy observation; all configuration, privilege, connection, query, missing-heartbeat and backlog errors return 1 without logging credentials or database errors. It does not itself send messages, schedule checks, prove historical completeness, or prove the next run will occur. The probe checks selected sensitive tables and elevated capabilities, not the login's complete privilege graph or security of the monitor host.

In synthetic PGlite and disposable PostgreSQL 17.6 tests, a separately created login can read the health signal but cannot read requests or invoke the job; missing/stale/future heartbeats and overdue work fail closed. An actual CLI test against a disposable TLS-enabled PostgreSQL instance succeeded with a trusted certificate and fresh heartbeat, and failed for an untrusted certificate, incorrect role and stale heartbeat. The separately installed test-only function also passed within the broader synthetic finance rollback rehearsal, and was absent after rollback. These are not hosted-identity, provider networking or actual alert-delivery tests. The boolean function is installed in development, but no independent monitor credential or monitor has been created on the connected project.

Before activation, review the complete login privileges and network/TLS configuration. After installing the scheduler and this function in the verified coordinated cutover, an authorized operator may grant only schema USAGE and function EXECUTE to a dedicated database login, and run the probe from an independent platform. Configure alerts for **non-zero exit and missed probe executions**; without a missed-run/dead-man check, stopping the monitoring service would itself go unnoticed. Test alert routing separately with approval before relying on it. GitHub Actions scheduled workflows can be delayed or dropped and operate from the default branch; neither merely adding a workflow to this draft nor a green manual probe establishes reliable monitoring.

## Recovery, disabling, and rollback

- If heartbeat is missing/stale or due count is nonzero, inspect provider job/run history, paused status, database connectivity, locks and exact SQL error. Keep the decision guards active; do not bypass them or manually issue payments. Repair the cause, then allow independent job transactions to retry. Do not assume a zero processed count means a clear backlog.
- To stop further execution, an authorized operator disables/unschedules the **specific verified job ID**, waits for any already-running transaction to finish, and confirms no later runs. Revoke the dedicated identity's execute and disable the health UI. Preserve logs, audit and rejection/notification records. Disabling scheduling does not undo committed rejections. If already persisted decisions require correction, use a reviewed human reconciliation procedure; do not silently change financial history.
- Reverting database objects/guards must follow an integrated, tested rollback plan that preserves history and handles old clients. Do not drop columns, remove audit evidence, re-enable unsafe legacy flows, or uninstall a shared extension blindly. Determine compatibility and dependencies first. After downtime, resume the minute job only after verification; repeated runs catch up older marked requests.

## Subsequent request-submission and scheduler checks

The weekly Supervisor form now preserves a random, actor-scoped **tab-local warning** before submitting a request. An ambiguous response or mismatched returned worker/site/submitter/amount leaves it in place, holds further submissions in that tab and requires explicit investigation and acknowledgement to clear it. A verified response clears the matching marker; if browser storage is unavailable or changes unexpectedly, the UI fails closed. The marker contains no worker or amount data. This is **not** a database idempotency key, automatic cancellation, cross-tab/device lock, durable storage or proof of non-submission. Closing the tab or clearing storage can lose the warning; an in-flight request may commit later, and older clients/direct APIs bypass it. The store also rejects mismatched returned fields before showing success. Synthetic UI tests cover lost responses after an insert into a small local database, remount, a changed marker and storage failure; they do not test hosted Auth/PostgREST.

A subsequent read-only development observation found job 4 active with the expected minute schedule and command, and five recent completed runs succeeded. The external-health function returned healthy with zero current remaining due and a recent heartbeat. The development queue was empty, so this is not a populated expiry test or independent failure/dead-man monitoring. No alert was configured or sent.

## Idempotent request submission candidate (held; default off)

`weekly_bale_idempotent_submission.sql` adds a separate, Supervisor-only RPC accepting a request UUID, worker, site, amount and expected Sunday start. It serializes the same UUID and returns an existing matching weekly request on retry. The existing site/window/audit/notification triggers still run for a new request. It checks the resulting weekly marker, so an unsaved retry for a previous week rolls back rather than creating a request in a later week. A replay returns the current stored status, not proof that money was released. It neither removes the old insert path nor makes two different UUIDs, old clients, other tabs/devices or a lost retry record idempotent.

A separately opted-in branch UI (`NEXT_PUBLIC_WEEKLY_BALE_IDEMPOTENT_SUBMISSION_PREVIEW`, default false) retains the exact sensitive request details and UUID in tab sessionStorage before sending and offers only that exact retry after an unconfirmed result. Same-origin scripts can read the details; storage may disappear on tab/browser changes. An older opaque warning is not treated as an exact retry. Clearing a warning never cancels an in-flight request. The existing tab warning remains the only protection when the separate flag is off. Neither flag nor a UI check authorizes database access.

Synthetic PGlite tests cover role/site denial, invalid and conflicting requests, audit rollback, old-week rollover and replay after the window; disposable PostgreSQL 17 tests exercise concurrent same-ID requests, and the full synthetic finance chain uses the RPC before release and payroll inside rollback. A synthetic UI-to-SQL test simulates a lost response after commit, remounts, retries the same request and checks that only one request, audit event and in-app notification exist; it uses a mocked store/transport and is not hosted Auth/PostgREST.
