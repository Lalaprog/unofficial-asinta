# Development expenses: anonymous privilege hardening

The Founder-only `public.expenses` table had RLS enabled and two authenticated policies: a permissive Founder policy and a restrictive session-assurance policy. There was no anonymous permissive policy. Nevertheless, anonymous had direct table-level `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `REFERENCES`, `TRIGGER` and PostgreSQL 17 `MAINTAIN` grants. RLS is not a general restriction on maintenance, trigger or reference privileges. Anonymous `TRUNCATE` was already denied. At inspection there were no explicit column ACLs or PUBLIC table grants, and neither `anon` nor `authenticated` inherited the other.

`supabase/release/development-expenses-anon-privileges.sql` (SHA-256 `34384d88b7fc5285d7c4cf386f820fa70d51134605eba3c5a7437085b1bfe10f`) is a narrow development-specific artifact. It locks the table with bounded timeouts, checks the observed owner, RLS policies, memberships and grants, revokes only `anon`'s table grants, and fails unless effective anonymous table and column privileges are absent and selected authenticated/service grants remain. It changes no expense records, Storage permissions, policies, helper functions, authenticated grants or service grants. It is not a generic migration. An authenticated user, a service role or a definer function still requires separate policy/privilege review; this is not a claim of complete security.

Synthetic PostgreSQL 17-compatible PGlite tests covered an anonymous read previously filtered by RLS, post-revoke denial, Founder read/write, low-assurance and non-Founder denials, rollback, and rejection on policy, column or PUBLIC grant drift. A hosted transaction on project `mchkdkjntnbwrgmyobpd` executed the artifact and rolled back; the previously present anonymous SELECT and MAINTAIN privileges were observed restored afterwards.

After the artifact was pinned and committed and PR checks passed, development migration **`20261114053654_development_revoke_anonymous_expense_privileges`** was installed on that project. Postflight catalog inspection found all eight tested anonymous table privileges absent, authenticated SELECT/INSERT/UPDATE/DELETE still present, service-role privileges unchanged, both expense policies still present, RLS enabled and the Founder/assurance helper hashes unchanged. The expense table contained zero rows. No financial rows were changed. This is not an authenticated browser or PostgREST test; actual authorized workflows still need verification.

Do not apply to another project or assume this locks out privileged owners, service-role callers or indirect definer operations. The artifact is targeted and non-idempotent; do not replay it on the installed project. No real client data should be used without recovery and release safeguards.
