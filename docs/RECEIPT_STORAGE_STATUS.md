# Receipt Storage — development review

The connected development bucket `receipts` was private at the catalog check. Its four authenticated Storage-object policies require `public.is_founder()`. The currently installed helper also calls `session_assurance_satisfied()`, so those four policies enforce the current assurance requirement **indirectly**, not through a separate restrictive Storage policy. This corrects the earlier PR comment which said assurance was not enforced. The conclusion depends on the current helper and policy inventory; new permissive policies or helper changes need a fresh review. Service-role access bypasses RLS and is not covered by this check. Existing signed URLs may remain usable until expiration.

The bucket's `file_size_limit` and `allowed_mime_types` were both null when inspected. This remains a server-side gap; client validation is not a security boundary, and a declared MIME is not proof that bytes are a valid image. Current branch code limits selection to 5 MiB, checks positive integer size, and supports JPEG (including `image/jpg`), PNG and WebP. It normalizes `image/jpg` to `image/jpeg` for both manual and inbox uploads by changing the **File type** as well as the option: the current Supabase JS SDK sends the File's MIME in its multipart form. A mock transport test checks the actual SDK multipart request; no hosted object was uploaded. The linked rental flow uses its existing expense, not another file upload. Existing objects are not modified by this code.

Before restricting the development bucket, coordinate with every deployed client: older clients may still upload `image/jpg`, so initially allowing the alias may be needed until the old client is replaced. Preserve the private flag and existing files. Supabase's [Storage schema guidance](https://supabase.com/docs/guides/storage/schema/design) treats Storage records as read-only and directs operations through the Storage API; do not directly update or delete bucket/object metadata with SQL. Use the supported bucket configuration API or dashboard, not a silent SQL alteration. This session's Supabase connector exposes database queries but no bucket-update operation; no privileged key was retrieved or written to chat. The actual Storage service's multipart MIME/size enforcement, object downloads, multi-photo and rental workflows must be verified with authorized real-account/device testing. A zero-byte placeholder existed in the development bucket at the metadata-only check; this observation does not imply a valid photo.

The branch now verifies the actual private object's size and SHA-256 before marking an inbox upload ready, including after an ambiguous upload response or existing object, and before attaching a saved photo to a manual expense. A failed or timed-out manual check does not attach the photo; manual expense entry without it remains available. The client checks are point-in-time only: the installed database guard still checks object existence, not bytes, and privileged/object writers can change an object later. AI scanning has its own check; neither verifies receipt validity or prevents duplicate expenses. Inbox pagination now checks PostgreSQL microsecond ordering rather than truncating to milliseconds. These code changes are not a hosted Storage test or a deployed client.

Database and Storage backups are separate; there is no verified restore. Do not use real client data before recovery and release safeguards are established.
