# Development website cutover (not client go-live)

The current website deployment is older than the installed development database. The development-only release path in this branch is intended to replace that website with the matching branch build, not to authorize real payroll, real client records, payments, messages, handover, or a production client launch. The connected database remains a development database. An on-screen banner marks the intended deployment; it is informational, not a security boundary.

## Release mechanism

The Vercel ignore step permits a production-target build only for this working branch when `ASINTA_DEVELOPMENT_RELEASE_SHA` is a 40-character lower-case Git SHA equal to `VERCEL_GIT_COMMIT_SHA`. All other production builds remain held. The build itself independently requires that branch and SHA, the development-site banner flag, the same enabled UI flags as the development preview, disabled automatic reminders, both expected project references, a matching public HTTPS Supabase URL and a nonempty public client key. It does not print the URL or keys. A forced build can bypass Vercel's ignore step, but not this build check if the checked-in npm build command is used; a different commit, build command or later settings can bypass either guard. This is a narrow temporary procedure tied to this development target, not a general installer.

Set `ASINTA_DEVELOPMENT_RELEASE_SHA` to the exact reviewed commit only immediately before a deliberate deployment. Remove or disable it after the cutover; a redeploy or a build with other source/configuration must not be assumed compatible. Environment variables affect new builds, not the already deployed site. No user credentials, email/SMS settings, real messages or financial data are modified by this procedure.

The current npm build checks the public URL and key presence, not key validity, the service-role key, database contents, function semantics, Auth, RLS, PostgREST, device behavior, cron or isolation. Selected functions were inspected on the development project and exercised in synthetic PostgreSQL, but actual authenticated populated flows have not been verified. Old browser tabs and deployments retain their old code; reloading or closing them may be necessary, and backend guards cannot cover privileged bypasses. The old production deployment is not a finance-compatible rollback for the changed development database; do not blindly restore it.

Before real data or client use, conduct the deferred real-account/device workflows, independent Bale-expiry monitoring, and a tested private backup/restore including database, Auth, Storage and configuration. The previously disabled public-repository backup workflow is not a usable backup. The project-cost review is bounded and not an automatically complete cost ledger. Keep the optional experimental case-binding and cross-site controls off.
