# Project-cost review ledger — development installation, incomplete costs

This experimental database/UI pair records a Founder review of either the bounded `project_cost_reconciliation_preview` snapshot or, when the separately gated combined historical review is available, the bounded `project_cost_historical_review` snapshot. It is **not a final project-cost ledger, an approved allocation of a correction, proof of payment, or a posting to finance**. The reviewed database draft is installed in the development finance cutover. The saved-review UI remains gated; the working-branch development cutover flag enables the coordinated gates, not production. The ordinary scratchpad still saves nothing. When both the combined-history and ledger UI gates are enabled, the saved-review controls are inside the combined panel; otherwise the base panel retains its saved-review controls. Do not enable the UI or include the SQL in a deployment without coordinated review of the other finance candidates, target schema and recovery.

## Behavior tested in synthetic databases

- A Founder with required session assurance chooses include or exclude for every returned expense. Each exclusion needs a human-written reason; an AI Bale hint or an assertion is not treated as proof. The linked rental remains the expense itself, not a second amount. Paid worker allocations contribute their gross, not gross plus Bale; Supervisor pay is outside this project snapshot.
- For a combined review, every returned historical attribution also requires an explicit include/exclude decision, with a reason for exclusion. The server rejects inclusion when any original-period case or overlapping same-worker voucher exists, including a draft at another site; exclusion can understate costs. Selected site gross is added once, while excluded historical gross is displayed separately. Neither the original gross nor Bale is added again.
- The server obtains a new bounded snapshot and rejects differences from the reviewed one, ignoring only capture time. It calculates centavo-scale totals from the server snapshot, saves the evidence, decisions, note, reviewer and monotonic per-project revision, and does not change expenses, payroll, advances, allocations or payments. Exact retries with the same request ID replay; different details fail. A competing revision or changed snapshot requires reload and review. Founder role is rechecked under a row lock. Repeatable-read transactions are rejected.
- A read of the latest or specified revision reports `matches`, `changed`, or `unavailable` for the **included sources at the read snapshot**, never a guarantee about subsequent changes. A later review creates a new revision and leaves the prior review immutable. Direct client access is revoked and authenticated RPC calls require Founder and assurance.
- The separate UI requires a reason for each excluded expense, a note and an acknowledgement that resets when the reviewed inputs change. It validates returned snapshots, decisions and totals, and allows browsing saved revisions. A sessionStorage marker contains only actor/project/request IDs and expected revision, not financial evidence. While mounted, an uncertain result can be retried with the exact in-memory input; after navigation, only the original revision can be checked. A missing or different revision is not proof of failure. Explicit marker clearing after independent investigation does not cancel an in-flight request or undo a review. Losing browser storage or changing tabs/devices can lose recovery context; independently inspect records. The marker is accessible to same-origin scripts and should not be considered secret.
- PGlite tests cover decisions, retry, changed/unavailable evidence, privileges and preservation. UI tests cover gating, input acknowledgement, malformed data, storage errors, unknown outcomes, navigation and revision browsing. An integrated synthetic UI-to-PGlite test loses a committed response and retries the same input, leaving one review and unchanged payroll; it also rejects a stale expense snapshot and exercises a fresh second review after explicit marker investigation. Independent local PostgreSQL 17 tests cover identical concurrent retry, competing revisions, an expense change during a lock wait and Founder demotion. A rollback-only, hosted-shaped synthetic finance rehearsal separately installs this draft and checks a Bale/rental/payroll review alongside a later settled correction.

## Important limitations and cutover work

The snapshot now includes bounded original-voucher adjustment case signals only for paid worker allocations returned for that site. A case may appear on multiple sites because it belongs to the whole worker voucher. Opening or resolving a matching case changes the included-source freshness check; a settlement record is not payment proof. **No correction is allocated or added to a project.** The base snapshot excludes externally paid/legacy payroll; the combined snapshot includes only explicitly selected, attributed historical worker gross, and still excludes unattributed or unselected external records. Both exclude correction cases not linked to included vouchers, correction project allocations, incomplete or missing allocations, unrecorded expenses and other sources. Thus `matches` is not completeness. Human exclusions can be wrong or duplicate costs elsewhere; the system does not validate external documents or discover duplicates automatically. All choices and notes are retained as sensitive data. A source can change immediately after the save/read, and nonfinancial changes not represented by the snapshot do not affect its status. It does not lock all source writers or make an accounting period final.

The snapshot requires the paid-adjustment candidate and its case table; missing prerequisites fail installation, not an assumed empty list. It supports at most 200 expenses, 500 paid allocations, 500 matching correction cases and a 1 MiB response. The combined response has a 2 MiB cap; the base response retains its own 1 MiB cap. The table definition changed during development and is not an upgrade migration: any earlier installed experimental ledger would need a separately reviewed migration and compatibility plan. A previous experimental snapshot without `adjustment_cases` will fail current client validation; test-only saved reviews created by an earlier draft need explicit compatibility planning, not silent upgrading. The reviewed versions were installed on the connected development project as part of the coordinated finance cutover; this document otherwise retains candidate-era design notes.

Before any usage, further test the UI on authenticated desktop/mobile devices, multiple tabs, real Auth/PostgREST and failure/recovery paths; reconcile historical payments and decide how original-period corrections should be evidenced and allocated without double counting; reconcile real records and duplicate handling; review privileges, inherited roles, ownership, locking/deadlocks, capacity/pagination, retention and audit; test the actual hosted schema and legacy/service writers; and establish verified backup/restore including Storage. The draft deliberately refuses oversized previews rather than yielding a partial amount.

The combined write re-reads one statement snapshot before recording, but does not lock every historical source or all voucher writers. A new case, voucher or other source may appear between that recheck and commit or immediately afterwards; freshness is advisory and must be rechecked. These controls do not certify that overlaps or duplicate expenses are absent outside the bounded evidence.
