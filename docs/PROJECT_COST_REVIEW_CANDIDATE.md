# Project-cost review ledger candidate — not installed

This isolated database experiment records an immutable Founder review of the existing bounded `project_cost_reconciliation_preview` snapshot. It is **not a final project-cost ledger, an approved allocation of a correction, proof of payment, or a posting to finance**. There is no client UI, feature flag or installation authorization for this draft. The existing scratchpad still saves nothing. Do not include this SQL in a deployment without coordinated review of the other finance candidates, target schema and recovery.

## Behavior tested in synthetic databases

- A Founder with required session assurance chooses include or exclude for every returned expense. Each exclusion needs a human-written reason; an AI Bale hint or an assertion is not treated as proof. The linked rental remains the expense itself, not a second amount. Paid worker allocations contribute their gross, not gross plus Bale; Supervisor pay is outside this project snapshot.
- The server obtains a new bounded snapshot and rejects differences from the reviewed one, ignoring only capture time. It calculates centavo-scale totals from the server snapshot, saves the evidence, decisions, note, reviewer and monotonic per-project revision, and does not change expenses, payroll, advances, allocations or payments. Exact retries with the same request ID replay; different details fail. A competing revision or changed snapshot requires reload and review. Founder role is rechecked under a row lock. Repeatable-read transactions are rejected.
- A read of the latest or specified revision reports `matches`, `changed`, or `unavailable` for the **included sources at the read snapshot**, never a guarantee about subsequent changes. A later review creates a new revision and leaves the prior review immutable. Direct client access is revoked and authenticated RPC calls require Founder and assurance.
- PGlite tests cover decisions, retry, changed/unavailable evidence, privileges and preservation. Independent local PostgreSQL 17 tests cover identical concurrent retry, competing revisions, an expense change during a lock wait and Founder demotion. A rollback-only, hosted-shaped synthetic finance rehearsal separately installs this draft and checks a Bale/rental/payroll review alongside a later settled correction.

## Important limitations and cutover work

The snapshot excludes externally paid/legacy payroll, paid-period adjustments, incomplete or missing allocations, unrecorded expenses and other sources. In the combined test, a later separately settled correction does **not** change the review's `matches` status: this deliberately demonstrates that matching included evidence is not completeness. No correction is allocated or added to a project. Human exclusions can be wrong or duplicate costs elsewhere; the system does not validate external documents or discover duplicates automatically. All choices and notes are retained as sensitive data. A source can change immediately after the save/read, and nonfinancial changes not represented by the snapshot do not affect its status. It does not lock all source writers or make an accounting period final.

Before any usage, design and test a safe UI with exact-retry recovery and explicit warnings; decide how historical payments and original-period corrections should be evidenced and allocated without double counting; reconcile real records and duplicate handling; review privileges, inherited roles, ownership, locking/deadlocks, capacity/pagination, retention and audit; test the actual hosted Auth/PostgREST/schema and legacy/service writers; and establish verified backup/restore including Storage. The 200-expense/500-allocation limits of the underlying snapshot remain. This draft deliberately refuses incomplete or oversized previews rather than yielding a partial amount.
