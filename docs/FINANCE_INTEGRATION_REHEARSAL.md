# Integrated finance rehearsal (synthetic PostgreSQL only)

This is a **test harness, not an installation bundle**. Do not point it at a shared, hosted, development, staging or production database. Rollback does not prevent DDL locks, and the opt-in test creates fixture tables and roles in its target database. Use a newly created, empty, locally isolated PostgreSQL 17 database with a name beginning `asinta_test_`; dispose of it afterwards. The fixture is synthetic and is not a clone of Supabase or the target schema. See [release reconciliation](RELEASE_RECONCILIATION.md) for deployment blockers.

Example, assuming a local isolated PostgreSQL instance is already running and its owner can create databases and the fixture roles:

```sh
createdb -h 127.0.0.1 -p 55432 -U postgres asinta_test_finance_rehearsal
FINANCE_INTEGRATION_REHEARSAL_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55432/asinta_test_finance_rehearsal \
  npx vitest run tests/finance-integration-rehearsal-postgres.test.ts
```

Use a **fresh database for each run**: setup persists the synthetic base fixture and marker even though candidate and scenario transactions roll back. Do not share the server with valuable databases: the fixture may create cluster-wide roles. The test validates an `asinta_test_*` database name and empty public schema but this is only a guardrail, not proof of isolation. Never embed credentials in documentation, CI logs or committed URLs.

`node scripts/build-finance-integration-rehearsal.mjs` prints the rollback-only SQL; it accepts no arguments and has no commit/deployment option. A generator unit test checks the ordered source hashes and boundary; a PostgreSQL test checks the marker, failure rollback and success rollback. For the end-to-end synthetic scenario only, the test removes the *final* rollback from an in-memory copy, runs the transaction and explicitly rolls it back after assertions. Do not modify or repurpose the script to commit.

## Connected UI-to-database rehearsal

The weekly release candidate now rechecks the worker's active, unique assignment while holding the worker lock: after a move or archive, or if the worker is already linked to a Supervisor account at the check, the old site's Supervisor cannot record a new release, and the Founder must review it. Account creation/role-change races are not serialized by this worker lock and need separate review. A release already recorded remains idempotently readable by an otherwise authorized caller. The release list exposes an assignment-review warning from its current snapshot; it can become stale immediately and is not permission to hand out cash. The race check depends on ordinary assignment/removal writers taking the same worker lock. A read-only development check found no anon/authenticated table or column assignment writes, and the observed guarded assignment and removal functions lock the worker; **service_role retains direct table write and TRUNCATE privileges** and can bypass that convention.

`assignment_writer_acl_cutover.sql` is a **separate, uninstalled** experimental restriction of direct assignment table/column writes for API roles, including service_role. It retains SELECT and the existing service-only guarded RPC entry points, fails if required definer RPCs/owner access are absent or if inherited writes survive, and must run in a transaction. It can break maintenance, restores, integrations and old server deployments that depend on direct writes. Synthetic PGlite tests exercise guarded creation/retry, assignment, archive/restore, atomic move and history after the revoke. In PostgreSQL 17, tests show that revocation waits for an already-running writer and that a writer waiting on the cutover lock is denied after commit; the integrated rollback rehearsal also tests the actual guarded assignment RPC. These are partial fixtures and do not prove hosted RLS, all writers or restore compatibility. Service-role RPCs accept an actor argument and still require a trustworthy server; owners/superusers, role inheritance changes, direct worker/account writes and disabled triggers remain privileged paths. Review exact function bodies, owners, grants, all deployed clients and recovery before any rollout; do not install this candidate alone. PostgreSQL tests simulate a concurrent move, but do not prove real PostgREST, physical release, every lock order or end-to-end deployment.

`tests/weekly-bale-payroll-workflow-integrated.test.ts` drives the actual experimental release and worker payroll components through their RPC interfaces into an in-memory synthetic PGlite database using the candidate SQL. It tests a simulated Wednesday release, attendance overtime and approved allowance, saved draft and revision-bound approval, Saturday external-payment recording and gross site allocation. Lost release and payment responses are simulated *after* their database commits; the UI reloads and reads the recorded results without sending another payment or release. A second scenario creates a draft before a Bale release, verifies stale approval is blocked, refreshes the saved draft to include the full release, and approves the revised amount without recording payment. The test uses mock authentication, an injected policy clock, simplified RLS/fixtures and direct local RPC calls; it is not a real browser, PostgREST, hosted Auth, mobile-device, concurrency, or external-payment test. Nothing is installed or transferred.

The weekly planning preview identifies the optional experimental voucher actions in its header and accessible table caption when enabled, rather than describing the entire screen as read-only. When the gate is off it remains clearly read-only. This is a display correction, not permission or deployment validation.

These facts can change immediately and must be checked again under the eventual cutover lock; they do not establish compatibility or permission to deploy.

The selected table policies also permit Founder writes to payroll and advances, and Supervisor request inserts. The request audit, notification and site-guard triggers and payroll finalized-field trigger were enabled. This is a starting list, **not** a complete writer inventory: keyword searches miss indirect calls, dynamic SQL, external/service and administrative writers, other tables, deployed clients and renamed objects. Attendance policies checked project assignment without proving worker membership. Recheck full definitions, grants, role inheritance, policies and all writers against the exact target before deployment. In the branch client, the expense AI proposal was an additional direct `createAdvance` route outside the Advances page; cutover mode now holds this shortcut while keeping expense entry available. Existing deployed/older clients remain unaffected, and server guards remain essential.

## Experimental legacy-writer cutover guards

`weekly_worker_legacy_cutover_guard.sql` and `weekly_bale_legacy_cutover_guard.sql` are **additional uninstalled drafts**, not part of the rollback generator or a deployment bundle. They must be reviewed together with the exact weekly workflow and installed only in an isolated, representative test transaction until the full rollout is ready. The worker guard checks for unresolved non-paid legacy vouchers under a table lock and rejects new unsourced payroll at transaction commit. The Bale guard checks for old open requests and outstanding unsourced advances under locks, rejects new unsourced advances at commit, and blocks manual/partial updates of a weekly release; the exact full deduction during the source-bound weekly payment remains allowed. Existing paid payroll and settled historical advances are not rewritten. An external historical assertion remains evidence, not a new transaction. The generator now also revokes and checks `service_role` access to protected source evidence.

The deferred checks are necessary because the legitimate functions insert the voucher/advance before their protected source/link in the same transaction. A client that forces constraints immediate before invoking those functions will fail; PostgREST transaction and error behavior must be verified in the target environment. Synthetic PGlite UI-to-SQL tests exercise a controlled release, failed manual deduction, revision-aware payment and gross site allocation. In isolated PostgreSQL 17, the combined finance rehearsal explicitly fires the deferred checks before its rollback. A separate committed test verifies both directions of a payroll-writer/cutover race: an older in-flight draft makes preflight fail, while an insertion waiting for the committed guard fails at its own commit. Another test shows an in-flight legacy advance makes Bale preflight fail after it commits, and exercises a controlled Bale release and full deduction. The tests do not cover every lock order, role, function, restore/service writer or real client.

`NEXT_PUBLIC_WEEKLY_WORKER_CUTOVER_PREVIEW` is a separate default-off **UI hold**, not authorization or an installation check. It hides the old payroll generate/approve/paid controls, legacy manual Bale and manual deduction controls, old request issuance, and the expense-page AI-detected Bale shortcut; saving an expense still works and no Bale is silently created. If the Bale gates are missing, request submission and review are held rather than reverting to legacy review. It intentionally hides old actions even when other weekly flags are misconfigured. Other old deployed clients and direct API calls do not see this hold, and the guards are not a complete defense against privileged users, disabled triggers, malformed historical data, legacy manual deductions outside linked weekly releases, RLS drift or unreviewed definer functions. They deliberately affect service/owner inserts, imports and restores. Existing historical records and external payments need reconciliation; no evidence proves that cash moved. A complete writer inventory, compatible client rollout, isolated target-compatible migration/rollback, scheduler and independent monitoring, real Auth/PostgREST/device checks, and recovery plan are still required before real use. Do not install either guard by itself or assume that zero selected legacy rows proves a safe cutover.

## What it proves and does not prove

The test exercises the combined installation and a synthetic operational flow rather than independently applying each candidate. It verifies missing-marker failure, rollback after a deliberately late collision, successful rollback and selected ACL/role failures. It checks worker gross and net in centavos, paid site allocation and history; a manual estimate with one confirmed rental and an excluded Bale-related expense; original paid voucher preservation after an externally settled correction case; two-site Supervisor attendance, leave summary/review and one company-wide payroll ledger; and direct invocation of overdue request expiry twice. The next week's new draft includes neither the resolved prior-period difference nor an expired request. System expiry audit has a null actor rather than falsely attributing the rejection to the submitter. Its SQL and business fixtures are rolled back and selected base-table fingerprints are compared.

`tests/helpers/finance-hosted-shape-fixture.sql` adds selected numeric precision, not-null, status, foreign-key and check constraints resembling the observed development schema; the expense-breakdown migration adds its real revision trigger. It remains a deliberately partial synthetic schema, with simplified policies, user/worker/site rows and authentication. In this fixture rental confirmation deliberately touches the expense row to protect against concurrent edits, so the legacy revision trigger increments the version. A later nonfinancial note edit increments it again; an amount edit is blocked. An old expense editor may therefore need to reload after confirmation. These assertions do not establish hosted compatibility or cover every trigger, constraint, grant or race.

The operational test additionally installs `project_cost_review_ledger.sql` inside its rolled-back transaction, outside the generated sequence. It records and retries an incomplete review, then shows that a separately settled correction for an included voucher changes the saved review's included-source freshness status. The whole-voucher case appears as a comparison signal; its difference is not allocated or added to the site estimate. See [candidate limitations](PROJECT_COST_REVIEW_CANDIDATE.md). This does not make the review a final cost or prove an external settlement.

This does **not** install any database objects on a shared system, activate feature flags, create a schedule, transfer money, send messages, verify actual accounts or prove live RLS, recovery or concurrent operation. The scratchpad alone does not persist choices; its separately gated saved-review UI uses the uninstalled ledger and is not authoritative. The test-only ledger record is rolled back. The single expense exclusion is a human decision, not automatic duplicate detection. Other candidates including assignment history and attendance guard are separately installed only inside the test transaction, while owned equipment and category catalog are not part of this sequence. Selected denial checks and fingerprints are not exhaustive. The marker, name check, tests and SQL tripwires do not authorize using the script against any shared or hosted database.

Before any real installation: separately reconcile the exact hosted catalog, existing functions, grants, policies, migration history, active/old clients and data; review all interacting drafts and lock orders; test restore/recovery and isolated target-compatible cutover; then explicitly plan and authorize deployment. No `supabase db push` or stale generated installation bundle is implied.
