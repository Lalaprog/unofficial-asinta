## Purpose and boundaries

A Founder with required assurance can return an **approved, unpaid** Supervisor period to draft with an explanation and explicit acknowledgement that no external payment has occurred. They can refresh a draft using reviewed current attendance, leave, identity and rate. The database recomputes the amount from locked current sources; pending conflicts, legacy overlap, changed expected sources, or changed identity fail closed. It preserves the original period and appends immutable before/after revision evidence. Approval and payment decisions must include the exact reviewed monotonic revision; stale attempts fail instead of applying to a different amount. Exact request retries return the original revision and do not repeat a transition. Payment recording remains a human statement, not a transfer; the system cannot verify that cash was not handed over. A paid row cannot be returned or refreshed and requires the existing separate original-period case workflow. Nothing automatically carries a correction into another period or posts a project cost.

The new event table is RLS-protected with direct API/service access denied and immutable event triggers; an owner can bypass safeguards. The candidate preserves the old ledger events as well as new full before/after snapshots. A Founder-facing revision-history summary is separately gated; its restricted read function was installed as `20261114011246_development_supervisor_revision_history`. The branch preview flag is set and a matching preview build has been requested. Full snapshots remain retained in the protected table; the screen shows a limited summary of post-upgrade revision events, not the earlier creation/decision history. Identity/name matching is only a risk signal. Other tabs/devices, loss of session storage, an ambiguous external payment, inherited privileges, privileged writers, deadlocks and outages still require investigation. A stopped retry does not cancel an in-flight request. A saved legacy decision retry cannot be resent from the upgraded UI; the original period must be inspected first. The matching UI rejects incomplete or incompatible revision responses and never silently falls back to the old writer.

## Verification and rollout conditions

Synthetic PGlite tests cover unpaid return, refreshed amounts, stale revision/snapshot refusal, unauthorized roles, lost-response exact retry, audit rollback, unchanged paid rows and the UI-to-SQL flow. A PostgreSQL 17 concurrency scenario is included in the existing isolated Supervisor ledger CI job for simultaneous stale confirmation and identical retry; inspect its actual result, not merely the presence of a test. These do not establish hosted Auth/PostgREST behavior, all writer paths, real-world payment, device usability or recovery.

For other environments or subsequent rollouts, review the exact hosted function definitions, role/column privileges, active data, other clients and pending requests; verify the artifact in a rollback-only transaction and prove the matching flagged build is ready. Disable old clients/decisions or communicate the incompatibility. Install atomically with guards and then verify effective grants, reads and the exact deployment. Keep alerts and tested recovery on the pre-real-use checklist; never use the migration to rewrite paid history or silently reconcile real money.
