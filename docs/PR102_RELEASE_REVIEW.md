# Draft PR #102: release review and remaining gates

This is a review checklist, **not approval to deploy** and not evidence of a successful hosted test. The connected `unofficial_asinta` database is development/demo but is also used by the existing application: changing it can affect other sessions. Keep the PR in draft until rollout and authenticated checks below are completed. The client must receive reviewed structure/configuration, not development business data or SMTP credentials.

## Findings from read-only development catalog inspection

- Before rollout the existing history, assurance, project access and guarded assignment functions existed, while the new PR functions, inbox table and expense index checked were absent; those feature objects are now installed as described below. The columns inspected for these migrations and the necessary base tables exist. This is not a complete schema or behavior equivalence check. Hosted migration versions/names differ from the repository; **do not blindly run `supabase db push` or the stale fresh-install bundle**.
- No worker has multiple active site-assignment rows in the current development snapshot. This is a point-in-time aggregate, not a promise about future changes or the final client database; do not remove or reconcile assignments without separate instruction.
- The `receipts` bucket is private and the existing four storage policies call `is_founder()`, but its `file_size_limit` and `allowed_mime_types` are both null. The application checks JPEG/PNG/WebP and 5 MiB, and the inbox table checks the claimed metadata, but these do **not** enforce actual bytes or content at the bucket for a direct Storage caller. The ready trigger verifies object visibility/existence, not MIME, size or digest. AI scanning compares downloaded bytes to the claimed digest; manual attachment does not. No separate restrictive MFA policy on `storage.objects` was observed, but a follow-up catalog inspection confirmed that all four current policies call `is_founder()`, and that helper calls `session_assurance_satisfied()`. Thus the currently observed policy/helper chain requires aal2 for enrolled users, while unenrolled users can use aal1. This is not a restrictive Storage policy: an additional permissive policy, helper change, signed URL, or privileged path has different implications. Authenticated hosted behavior has not been tested. Review compatible bucket restrictions and existing integrations before changing the bucket. No bucket setting was changed.
- The existing `anon` and `authenticated` roles are NOLOGIN and lacked public-schema CREATE in this inspection, and previously had `TRUNCATE` privilege on several existing business tables, including attendance, expenses and payroll. PostgreSQL RLS does not apply to TRUNCATE. This is a privilege finding, **not a demonstrated public API exploit**: a SQL execution path under one of those roles would be required, and none was tested here. The existing user-profile table also has a truncate-blocking trigger. The reviewed `20261112000006_revoke_client_truncate.sql` was applied to the development project with authorization as hosted migration `20261111224207_revoke_client_truncate` (different version from the repository). It removes this privilege only from those two roles on the explicitly listed existing tables; it preserves other grants and service-role privileges, and aborts if an inherited grant still permits TRUNCATE. It does not change default privileges or cover future tables. Review other privileges, defaults, role memberships and SQL execution paths separately. Afterward, catalog checks found no anon/authenticated TRUNCATE privileges on any of the 26 existing public tables and confirmed service-role TRUNCATE remains on all 26. No rows were modified by this migration. This is point-in-time privilege verification, not an authenticated application smoke test.
- The checked-in fresh-install bundle is stale, and this PR is not a complete clean-client deployment package. Verify schema-only install, RLS, storage, Auth/Realtime setup and catalog parity separately in a disposable environment before client transfer.

## Repeating the local assignment race test

With the dependencies installed, create a **new empty disposable local** PostgreSQL database named `asinta_test_*`, using a local test cluster with permission to create the fixture roles. Run `ASSIGNMENT_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55432/asinta_test_assignment npx vitest run tests/single-project-assignment-concurrency.test.ts`, substituting your actual local port/database. The test creates schemas, roles and tables and deletes fixture assignments between cases. It refuses non-local hostnames or a nonmatching database name and checks that its target schemas are empty, but do not use a valuable cluster: roles are cluster-wide. It is opt-in and skipped in normal CI without the variable. This test used PostgreSQL 17.6 and simplified fixture schemas, not the live Supabase stack.
