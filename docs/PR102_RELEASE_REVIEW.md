# Draft PR #102: release review and remaining gates

This is a review checklist, **not approval to deploy** and not evidence of a successful hosted test. The connected `unofficial_asinta` database is development/demo but is also used by the existing application: changing it can affect other sessions. Keep the PR in draft until rollout and authenticated checks below are completed. The client must receive reviewed structure/configuration, not development business data or SMTP credentials.

## Findings from read-only development catalog inspection

- The existing history, assurance, project access and guarded assignment functions exist; the new PR function names, inbox table and expense index checked were not found. The columns inspected for these migrations and the necessary base tables exist. This is not a complete schema or behavior equivalence check. Hosted migration versions/names differ from the repository; **do not blindly run `supabase db push` or the stale fresh-install bundle**.
- No worker has multiple active site-assignment rows in the current development snapshot. This is a point-in-time aggregate, not a promise about future changes or the final client database; do not remove or reconcile assignments without separate instruction.
- The `receipts` bucket is private and the existing four storage policies call `is_founder()`, but its `file_size_limit` and `allowed_mime_types` are both null. The application checks JPEG/PNG/WebP and 5 MiB, and the inbox table checks the claimed metadata, but these do **not** enforce actual bytes or content at the bucket for a direct Storage caller. The ready trigger verifies object visibility/existence, not MIME, size or digest. AI scanning compares downloaded bytes to the claimed digest; manual attachment does not. No separate restrictive MFA policy on `storage.objects` was observed in the catalog; the inbox metadata has its own MFA policy, which does not by itself protect direct Storage access. Verify the effective Storage authorization and assurance behavior before deciding on a policy change. Review compatible bucket restrictions and existing integrations before changing the bucket. No bucket setting was changed.
- The existing `anon` and `authenticated` roles are NOLOGIN and lacked public-schema CREATE in this inspection, but have direct `TRUNCATE` privilege on several existing business tables, including attendance, expenses and payroll. PostgreSQL RLS does not apply to TRUNCATE. This is a privilege finding, **not a demonstrated public API exploit**: a SQL execution path under one of those roles would be required, and none was tested here. The existing user-profile table also has a truncate-blocking trigger. The new, unapplied `20261112000006_revoke_client_truncate.sql` removes this privilege only from those two roles on the explicitly listed existing tables; it preserves other grants and service-role privileges, and aborts if an inherited grant still permits TRUNCATE. It does not change default privileges or cover future tables. Review other privileges, defaults, role memberships and SQL execution paths separately. No role grants were changed on the hosted database.
- The checked-in fresh-install bundle is stale, and this PR is not a complete clean-client deployment package. Verify schema-only install, RLS, storage, Auth/Realtime setup and catalog parity separately in a disposable environment before client transfer.

## Migration and release order

1. Confirm target and access, inventory migration history and function/table definitions, review backups/recovery and agree on a maintenance window. Never put passwords or keys in chat. Confirm the current app's compatibility while the database changes ahead of app deployment; the assignment guard changes an existing function's behavior, so an old UI may show a generic failure for a second assignment.
2. Validate the exact reviewed migrations in a disposable PostgreSQL/Supabase environment with representative RLS, storage and authenticated sessions. Apply only the required, explicitly reviewed SQL, in dependency order: `20261112000000` (assignment; requires existing `app_private.lock_project_worker_access` and project worker tables), `...001` (payslip read), `...002` (project calendar), `...003` (expense ledger and index), `...004` (receipt inbox), `...005` (history calendar), `...006` (client TRUNCATE revoke). The expense index uses non-concurrent creation and can block writes; plan accordingly. Migration `...006` requires every named table to exist and fails if privileges are inherited after revocation.
3. Compare grants, functions, policies, storage settings and migration records after installation. Confirm new functions have only intended execution grants, receipt metadata RLS is active, the bucket remains private, normal app CRUD still works, and service-role privileges are unchanged. Do not assume an error means all earlier separate migration transactions rolled back; inspect status before retrying. No blanket down migration is provided: dropping inbox metadata may orphan or hide saved photos, and changing grants back can reintroduce risk. Prepare feature-specific recovery before rollout.
4. On an isolated environment or with separate approval for test records/photos, verify Founder and Supervisor permissions (including MFA), calendar filters/pagination, failure/retry, saved-photo creation/resumption/scan, project expenses, single-site assignment races and payslip printing. Never send real messages or record real payments for testing. Local PGlite/UI tests and a disposable local PostgreSQL concurrency fixture are not hosted Auth, Storage, PostgREST or device tests. Real A4/browser readability also remains unverified.
5. Recheck PR CI, arrange authenticated desktop/mobile review and obtain a release decision. Only then consider merging/deploying. Keep the next major payroll/Bale/leave work separate; period helpers and read-only payslip printing do not implement the agreed payroll rules.

## Repeating the local assignment race test

With the dependencies installed, create a **new empty disposable local** PostgreSQL database named `asinta_test_*`, using a local test cluster with permission to create the fixture roles. Run `ASSIGNMENT_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55432/asinta_test_assignment npx vitest run tests/single-project-assignment-concurrency.test.ts`, substituting your actual local port/database. The test creates schemas, roles and tables and deletes fixture assignments between cases. It refuses non-local hostnames or a nonmatching database name and checks that its target schemas are empty, but do not use a valuable cluster: roles are cluster-wide. It is opt-in and skipped in normal CI without the variable. This test used PostgreSQL 17.6 and simplified fixture schemas, not the live Supabase stack.
