Update the observations below before acting; they describe one point in time and are not a live monitor. A complete tested recovery plan may be finished after development, but is required before real client data or handover.

## Read-only legacy finance risk summary

`supabase/preflight/legacy_finance_risk_summary.sql` is an operator-only, aggregate snapshot of selected legacy payroll, Bale and request-link signals. It returns counts, not identities or individual amounts, and changes no records. Run it with complete visibility; an RLS-limited account can give misleadingly low counts. Overlapping periods, nonweekly periods, arithmetic differences and differing request/advance amounts are leads for manual review, not automatic proof of duplicate payments or errors. Nonweekly periods can be legitimate Supervisor periods, and this check does not establish a worker's identity or whether money was actually paid. It does not compare historical external evidence, missing records, project costs, or other finance sources. Do not use a zero result as authorization to deploy or reconcile.

## Finance metadata and attendance scope findings

`supabase/preflight/finance_catalog_inventory.sql` is a read-only, selected metadata inventory: it reports absent roles/tables, selected column-type differences and candidate name collisions, column null/default flags, effective table grants, explicit column ACLs, RLS flags, and constraint/trigger/policy/function fingerprints. It returns no business rows. It is not a complete diff or an install verdict: effective SQL grants alone do not prove RLS access, definer functions and inherited column privileges require independent review, hashes can differ for harmless definitions or environments, and matching hashes do not establish semantic safety. The query was tested on disposable databases; it was not run as a full report against the hosted project in this batch.

Separate read-only catalog checks on the connected development database found the 15 selected financial numeric/type probes matched the expected shape. The checked tables had RLS enabled, and the attendance, payroll and expense triggers/constraints were inventoried. Some broad SQL grants exist for `anon` and `authenticated`, while the observed permissive policies on those tables target authenticated roles; grants alone are not evidence of anonymous data access or safety. Supervisor tables lack anon/authenticated table grants. These observations are a partial snapshot, not a role simulation, full policy review or proof of actual Auth/PostgREST behavior.

**Open scope gap:** the observed Supervisor attendance INSERT and UPDATE policies check assignment to the *project*, not the worker's active membership. The UI normally filters the Roll Call roster, but a direct client or stale/moved-worker record is not proven to receive the same worker-level protection from this policy alone. The legacy UI also automatically includes the Supervisor's site-based self-attendance, while the new general daily Supervisor workflow is uninstalled. A client-side check now refuses to submit edited moved-worker rows for a Supervisor, retains the local draft and directs the user to the Founder. It is a UX check, not a security boundary, and it cannot prevent races after its last read.

`supabase/drafts/attendance_assignment_guard.sql` is an **uninstalled candidate**, not a complete fix on the connected site. It requires current active single-site worker assignment for Supervisor attendance INSERT/UPDATE, rejects Supervisor identity changes, pins actor/site/worker rows to coordinate selected guarded moves and access removal, and preserves Founder backfill. Existing historical rows stay readable, but edits after a worker moves require the Founder. For compatibility it still permits a Supervisor's *own* legacy site self-entry; this exception is not the new once-per-person daily attendance model. It rejects writes without an authenticated actor (including maintenance/service jobs with no `auth.uid()`), requires READ COMMITTED, can block or deadlock under multi-row batches/other lock orders, and depends on all assignment writers using compatible worker locks; privileged direct assignment writers can bypass that coordination. Runtime lock waits are not bounded by its installation-only timeout. It does not enforce `recorded_by`, validate employee identity matching or fix broad worker-read policies. Install it only after service/restore paths, old clients, exact hosted catalog, multi-row lock ordering/load, history/draft UX and coordinated Supervisor payroll cutover have been reviewed and tested. Synthetic PostgreSQL tests cover selected upserts, rollback, move/deactivation/access-revocation races, and the combined finance fixture; they do not prove hosted Auth/PostgREST or full compatibility. No policy or access was changed on the connected site.

## Temporary deployment hold in this branch

`vercel.json` configures `scripts/vercel-release-hold.sh` as Vercel's ignored build step. It permits preview/development builds and cancels production or unknown environments. Its effect is limited to deployments that actually include and execute this file. It is **not active on current main or the existing recovery deployment before this branch is merged**. A deployment from older commits, an edited/removed guard, or a forced redeploy/promotion may bypass it. The hold does not change database permissions or disable payments/messages. Vercel counts canceled builds against deployment quotas. Do not assume the existing site is protected by this branch alone.

The owner or release operator must also control Vercel's project-level deployment settings and avoid deploying current main/old commits until reviewed. This repository-level hold cannot replace that operational control. If system environment variables are not exposed, the script holds the build rather than guessing; a canceled build does not prove the application is safe.

## Staged path to a safe engineering merge and later release

1. **Inventory first.** Recheck exact production SHA, main and PR SHA, Vercel aliases/settings, feature-flag targets and the actual hosted DB catalog/permissions. Use aggregate, read-only checks; do not print credentials, insert demo records, or assume preview uses an isolated backend.
2. **Reconcile schema by exact state.** Map each required RPC/table/trigger to what is actually installed, including bodies, grants and dependencies. Prepare atomic, state-aware scripts and rehearse them in a disposable PostgreSQL 17 database. Skip or verify already-installed objects rather than replaying old migrations. Keep unfinished finance and equipment flags off. Review direct privileged and old-client paths independently of UI flags.
3. **Test the candidate, not just its build.** Verify Founder and Supervisor authentication/MFA, assigned-site access, existing dashboard/attendance/expense flows, old and new UI paths and error behavior on desktop and mobile. Do not perform real payments or send messages. A preview can use the same database; do not write new records without permission. Confirm the planned rollback target is still available and compatible with any DB changes.
4. **Separate merge from feature completion.** An engineering-only merge can be considered once the precise deployment behavior and current-compatible screens are verified, with unfinished work disabled and PR scope accurately stated. It is not approval to use payroll or equipment as a finished feature. The present PR remains draft until that release behavior is actually verified.
5. **Release deliberately.** Once candidate SHA and database are verified together, review and remove or replace the checked-in hold in an intentional release commit. Verify the actual Vercel production alias, the resulting commit, build settings and flags after promotion; keep a compatible rollback procedure. A forced deployment can skip the ignore step and must not be used as a shortcut around unresolved checks.
6. **Finish business requirements separately.** Weekly worker payroll, Bale timing/release and same-period deductions, paid-period corrections, Supervisor payroll, durable project costs, rentals and remaining workflows require implementation and end-to-end tests before client-ready claims. Preserve identity and financial history; corrections must not auto-carry forward.
7. **Before real data/handover:** test a private, access-controlled complete recovery procedure covering database, Auth identities, Storage objects and configuration, and verify a restore. The disabled public-repository workflow is not a backup; no verified live backup exists. Client transfer must exclude demo data and retain structure, roles and access.

Do not execute destructive cleanup without a separately confirmed scope. No real payment or message is authorized by this procedure.
